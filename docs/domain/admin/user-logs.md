# UserLog

**Документ:** `docs/admin/user-logs.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

`UserLog` содержит техническую и административную историю событий, связанных с конкретным `User`.

UserLog является частью административной подсистемы и используется для диагностики, анализа безопасности и восстановления контекста действий пользователя.

UserLog не заменяет `Audit`.

---

# Ответственность

UserLog отвечает за:

* фиксацию технических событий User;
* историю аутентификации;
* историю административной активности;
* технические сведения, необходимые для диагностики;
* корреляцию событий User.

UserLog не отвечает за:

* бизнес-правила Bot;
* авторизацию;
* состояние Flow;
* историю Conversation;
* хранение Notification;
* замену Audit.

---

# UserLog и Audit

Эти механизмы имеют разную ответственность.

```text
UserLog
→ история и технический контекст User

Audit
→ значимые административные действия системы
```

Одна операция может создавать обе записи.

Например:

```text
User publishes Flow
        │
        ├── UserLog
        │
        └── Audit
```

---

# Основные свойства

| Свойство    | Назначение                        |
| ----------- | --------------------------------- |
| id          | Внутренний идентификатор          |
| user_id     | User, к которому относится запись |
| event       | Тип события                       |
| result      | Результат события                 |
| ip_address  | IP, если хранение разрешено       |
| user_agent  | User-Agent, если требуется        |
| metadata    | Дополнительные безопасные данные  |
| occurred_at | Время события                     |

Конкретный набор полей зависит от требований приложения и безопасности.

---

# Типы событий

Примеры:

```text
login.success
login.failed
logout
session.created
session.revoked
password.changed
mfa.changed
bot.created
bot.updated
flow.opened
flow.published
broadcast.started
```

Список расширяется по мере необходимости.

---

# Результат

Event должен иметь явный результат.

Например:

```text
Success
Failure
Denied
Cancelled
```

Неуспешные операции особенно важны для диагностики и безопасности.

---

# Аутентификация

UserLog может фиксировать события:

```text
login.success
login.failed
logout
session.created
session.revoked
```

Для входа могут храниться технические признаки:

```text
ip_address
user_agent
```

при условии соответствия privacy policy.

Пароли и секреты никогда не записываются.

---

# Административная активность

UserLog может фиксировать общую активность User:

```text
Flow opened
Broadcast created
Bot updated
Settings changed
```

Для значимых бизнес-действий отдельная запись Audit остаётся обязательным источником административного аудита.

---

# Metadata

Metadata может содержать безопасный технический контекст.

Например:

```json
{
    "resource_type": "Flow",
    "resource_id": 125,
    "code": "checkout"
}
```

Metadata не должна содержать:

* passwords;
* authentication tokens;
* API keys;
* secret values;
* необязательные персональные данные.

---

# Просмотр

Обычный User может просматривать только собственную историю, если такая возможность предусмотрена интерфейсом.

Системный администратор может иметь право просмотра истории других User.

Например:

```text
user-log.view-own
user-log.view
```

---

# Фильтрация

Административный интерфейс может предоставлять фильтрацию по:

```text
event
result
date range
IP
```

При наличии прав может использоваться фильтрация по User.

Фильтрация выполняется на сервере.

---

# Связь с Session

UserLog может ссылаться на Session, если это необходимо для расследования событий входа.

Например:

```text
login.success
    ↓
Session #123
```

Session остаётся отдельной сущностью безопасности.

---

# Изменяемость

UserLog является исторической записью.

После создания запись не редактируется обычными административными средствами.

Исправления выполняются через создание новых событий, а не переписывание прошлого.

---

# Удаление

UserLog не обязан храниться бессрочно.

Удаление старых записей выполняется в соответствии с отдельной политикой хранения и требованиями безопасности.

Критически важные записи могут иметь более длительный срок хранения.

---

# Безопасность

UserLog может содержать техническую информацию о входах и активности User.

Поэтому:

* доступ к UserLog ограничивается permissions;
* секреты не сохраняются;
* чувствительные поля должны быть минимизированы;
* экспорт требует отдельного разрешения, если он поддерживается.

---

# Аудит доступа

Доступ к UserLog может сам аудироваться, если это требуется политикой безопасности.

Особенно чувствительными являются операции:

```text
user-log.view
user-log.export
```

---

# Производительность

UserLog потенциально содержит большой объём данных.

Хранилище должно поддерживать:

* индексацию по user_id;
* индексацию по event;
* фильтрацию по времени;
* постраничное чтение.

Конкретные индексы определяются Infrastructure.

---

# Инварианты

Всегда должны соблюдаться следующие правила:

* UserLog относится к одному User;
* UserLog является исторической записью;
* секреты не сохраняются;
* UserLog не заменяет Audit;
* UserLog не определяет права User;
* обычное редактирование User не изменяет исторический UserLog;
* доступ к UserLog контролируется permissions.

---

# Будущие возможности

Архитектура допускает:

* корреляцию событий по request ID;
* device history;
* anomaly detection;
* security alerts;
* интеграцию с SIEM;
* расширенный анализ административной активности.
