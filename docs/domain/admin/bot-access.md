# Bot Access

**Документ:** `docs/admin/bot-access.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

`docs/admin/bot-access.md` описывает административный механизм управления доступом `User` к конкретному `Bot`.

Бизнес-модель связи `User ↔ Bot` описана в `docs/domain/bot-access.md`. Настоящий документ описывает её применение в административной подсистеме: выдачу, изменение, отзыв и контроль видимости доступа.

---

# Основной принцип

Доступ к Bot состоит из двух независимых компонентов:

```text
User
  │
  ├── Global Permissions
  │
  └── BotAccess
          │
          └── Role / Bot-level Permissions
```

Наличие глобального permission не означает автоматически доступ ко всем Bot, кроме специальных системных permissions, для которых такой обход явно предусмотрен.

Наличие BotAccess без необходимых permissions также не даёт права выполнять любую операцию внутри Bot.

---

# Видимость Bot

Обычный User должен видеть только:

* Bot, которые он создал;
* Bot, к которым ему предоставлен действующий BotAccess.

Таким образом список Bot в административной панели всегда строится с учётом доступа.

```text
User
  │
  ▼
Доступные Bot
  │
  ├── Created by User
  └── Granted via BotAccess
```

---

# Создание Bot

При создании Bot через административную панель:

1. создаётся Bot;
2. создаются его обязательные настройки;
3. создаётся BotAccess для User, выполнившего создание;
4. User получает роль владельца или другую роль, определённую политикой системы.

После завершения операции созданный Bot становится доступен создавшему User.

---

# Выдача доступа

User с permission:

```text
bot-access.grant
```

может предоставить другому User доступ к Bot.

В административной панели операция выполняется в контексте конкретного Bot:

```text
Bot
  ↓
Access
  ↓
Add User
  ↓
Select Role
  ↓
Grant Access
```

Выдаваемая роль не должна предоставлять больше полномочий, чем разрешено текущему User политикой RBAC.

---

# Изменение доступа

Для действующего BotAccess администратор может изменить роль или другие разрешённые параметры доступа.

Изменение должно проходить через Application Use Case.

```text
MoonShine
   ↓
UpdateBotAccess
   ↓
Authorization
   ↓
BotAccess
```

Изменение не должно напрямую модифицировать Eloquent Model из UI-логики, если операция содержит бизнес-правила.

---

# Отзыв доступа

Доступ может быть отозван User с permission:

```text
bot-access.revoke
```

После отзыва:

* Bot исчезает из обычного списка доступных Bot;
* доступ к Flow запрещается;
* доступ к Broadcast запрещается;
* доступ к Conversation запрещается;
* доступ к BotMember запрещается;
* доступ к BotSettings запрещается.

Исторические действия User не изменяются.

---

# Временный доступ

Если для BotAccess используется срок действия, административная панель должна отображать его явно.

Например:

```text
User: Ivan
Role: Operator
Expires: 31.08.2026
Status: Active
```

После истечения срока BotAccess считается недействующим автоматически.

---

# Роли

В интерфейсе управления доступом User выбирает роль, действующую в рамках конкретного Bot.

Примеры:

```text
Owner
Administrator
Operator
Support
Analyst
Content Manager
```

Конкретный список ролей определяется системой RBAC и не должен быть жёстко зашит в MoonShine Resource.

---

# Permissions роли

Перед подтверждением выдачи доступа административный интерфейс должен позволять определить, какие permissions предоставляет выбранная роль.

Например:

```text
Operator

✓ bot.view
✓ conversation.view
✓ member.view
✗ flow.publish
✗ broadcast.send
```

Фактическая авторизация выполняется сервером и не зависит от отображения этого списка в UI.

---

# Защита от повышения полномочий

User не может выдать другому User роль или набор permissions, превышающий собственные разрешённые полномочия, если это запрещено RBAC-политикой.

Например:

```text
Operator
```

не может выдать:

```text
Owner
```

только потому, что такая роль доступна в интерфейсе.

Сервер обязан повторно проверить это правило при сохранении.

---

# Самостоятельный доступ

Создатель Bot получает доступ автоматически в рамках сценария создания.

Для уже существующего Bot наличие User в системе само по себе не создаёт доступ.

```text
User существует
       ≠
User имеет доступ ко всем Bot
```

---

# Доступ к дочерним ресурсам

Все дочерние ресурсы должны проверяться относительно Bot, к которому они принадлежат.

Например:

```text
Bot
├── Flow
├── FlowDraft
├── FlowVersion
├── Broadcast
├── Conversation
├── BotMember
├── BotSettings
└── Localization
```

Наличие прямой ссылки на Flow или Conversation не должно позволять обойти BotAccess.

---

# Фильтрация списков

Ограничение доступа должно применяться на уровне запроса и Application Policy, а не только после получения полного списка.

Нежелательный подход:

```text
Загрузить все Bot
       ↓
Отфильтровать в PHP
```

Предпочтительный принцип:

```text
User
 ↓
Accessible Bot Query
 ↓
Только разрешённые Bot
```

Конкретная реализация относится к Application/Infrastructure.

---

# Контекст выбранного Bot

После выбора Bot административный интерфейс должен работать в контексте этого Bot.

Например:

```text
MVBotsHub
    ↓
Support Bot
    ↓
Flows
Broadcasts
Conversations
Members
Settings
```

Переход на другой Bot должен повторно устанавливать и проверять контекст доступа.

---

# Отзыв собственного доступа

Пользователь не должен случайно лишать себя последнего административного доступа к Bot, если это приводит к невозможности управления Bot.

Перед отзывом последнего критически необходимого доступа система должна выполнить проверку политики владения и управления.

Например, для Bot должен оставаться хотя бы один User, способный выполнять обязательные административные операции, если это является требованием политики проекта.

---

# Аудит

Следующие операции должны фиксироваться в административном аудите:

```text
Grant
Update
Revoke
Restore
Change Role
Change Expiration
```

В аудите должны быть доступны как минимум:

```text
Actor User
Target User
Bot
Old Role / State
New Role / State
Date / Time
```

---

# Notifications

Изменения BotAccess могут сопровождаться административным уведомлением User.

Например:

```text
Вам предоставлен доступ к Bot «Support»
Роль: Operator
```

Notification является частью административной подсистемы и не заменяет сам BotAccess.

---

# Безопасность

Проверка доступа обязательна на серверной стороне.

Недостаточно:

* скрыть Bot из меню;
* скрыть кнопку;
* исключить Resource из навигации.

Прямой запрос к API или административному маршруту должен проходить те же проверки.

---

# MoonShine

MoonShine предоставляет интерфейс управления BotAccess, но не является источником авторизационных правил.

MoonShine отвечает за:

* формы;
* таблицы;
* фильтрацию UI;
* визуальное отображение ролей и статусов.

Application/Domain отвечают за:

* допустимость выдачи доступа;
* изменение роли;
* отзыв;
* ограничения RBAC;
* сохранение согласованного состояния.

---

# Инварианты

Всегда должны соблюдаться следующие правила:

* User без действующего BotAccess не видит Bot обычными средствами административной панели;
* BotAccess и глобальные permissions проверяются независимо;
* User не может выдать полномочия выше допустимого уровня;
* доступ к дочерним ресурсам не может обходить доступ к Bot;
* отзыв доступа не удаляет историю действий;
* UI не является механизмом безопасности;
* создание Bot автоматически предоставляет доступ создавшему User;
* критические изменения BotAccess аудируются.
