# MVBotsHub

**Документ:** `docs/admin/README.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

Административная подсистема MVBotsHub предоставляет пользователям системы (`User`) интерфейс и механизмы управления платформой.

Административная подсистема отвечает за:

* управление пользователями системы;
* управление ролями и permissions;
* управление доступом пользователей к Bot;
* управление Bot и связанными ресурсами;
* управление Flow;
* управление Broadcast;
* просмотр Conversation и участников Bot;
* работу с системными настройками и аудитом.

Административная подсистема не является частью пользовательской модели Telegram-бота.

---

# User

`User` — пользователь MVBotsHub, работающий в административной подсистеме.

User не является `Person` и не является `BotMember`.

```text
User
 │
 ├── работает с MVBotsHub
 │
 └── имеет доступ к Bot через BotAccess
```

Физическая модель пользователя находится в текущей реализации приложения в:

```text
App\Models\User\User
```

Однако архитектурная документация использует термин `User` независимо от физического расположения PHP-класса.

---

# Разделение User и Person

Административная подсистема разделяет сотрудников системы и участников Telegram-ботов.

```text
User
 │
 └── управляет Bot

Person
 │
 └── взаимодействует с Bot
```

User не должен использоваться для идентификации участника Telegram-бота.

Person не получает доступ к административной панели только потому, что взаимодействует с Bot.

---

# Уровни доступа

Доступ в системе определяется двумя независимыми уровнями.

## Глобальный уровень

Глобальные роли и permissions определяют, какие возможности вообще доступны User в MVBotsHub.

Например:

```text
user.manage
bot.create
system.settings.manage
```

---

## Уровень Bot

`BotAccess` определяет, с какими конкретными Bot User может работать.

Например:

```text
User A
 ├── Bot A → доступ есть
 ├── Bot B → доступа нет
 └── Bot C → доступ есть
```

Пользователь административной панели должен видеть только те Bot, к которым имеет действующий доступ, если у него нет специального глобального permission для обхода этого ограничения.

---

# BotAccess

BotAccess является механизмом связывания User и Bot.

Он определяет:

* наличие доступа;
* роль User внутри Bot;
* дополнительные ограничения;
* срок действия доступа, если он используется.

Подробная модель описана в:

`docs/domain/bot-access.md`

---

# Видимость Bot

В обычном режиме пользователь административной панели видит только:

* Bot, которые он создал;
* Bot, к которым ему предоставлен BotAccess.

Доступ к отдельному ресурсу Bot не должен обходить проверку доступа к самому Bot.

Например, наличие URL на Flow не должно позволять открыть Flow, если User не имеет доступа к соответствующему Bot.

---

# MoonShine

MoonShine является Presentation Layer административной подсистемы.

```text
app/MoonShine
```

физически находится в корне `app`, но архитектурно относится к Presentation.

MoonShine отвечает за пользовательский интерфейс и не является источником бизнес-правил.

Бизнес-операции должны выполняться через Application/Domain, а проверки доступа должны быть централизованы и не зависеть только от MoonShine Resource.

# Правило контекста Bot

После выбора Bot административная подсистема должна работать в контексте конкретного Bot.

Например:

```text
MVBotsHub
    ↓
Bot: Support
    ↓
Flows
Broadcasts
Conversations
Members
Settings
```

Все операции с дочерними ресурсами должны проверять принадлежность ресурса выбранному Bot.

# Conversation

Административная подсистема может предоставлять просмотр диалогов и истории сообщений.

При просмотре Conversation должны соблюдаться права доступа User к соответствующему Bot.

История сообщений не должна изменяться через обычный административный интерфейс.

---

# BotMember

Администратор или оператор может просматривать участников Bot в пределах предоставленных ему permissions.

Доступ к персональным данным Person должен контролироваться отдельно от общего права просмотра BotMember, если это необходимо политикой безопасности.

---

# Аудит

Критические административные действия должны фиксироваться в аудите.

Например:

```text
создание Bot
выдача BotAccess
отзыв BotAccess
изменение роли
публикация Flow
запуск Broadcast
изменение системных настроек
```

Аудит не должен зависеть от конкретного UI.

---

# Application Layer

MoonShine не должен напрямую реализовывать сложные бизнес-операции.

Общая схема:

```text
MoonShine
   ↓
Application Use Case
   ↓
Domain
   ↓
Infrastructure
```

Это позволяет в дальнейшем выполнять те же операции через API, Console или другие интерфейсы без дублирования бизнес-логики.

---

# Безопасность

Административная подсистема должна проверять как минимум:

```text
User authenticated
        ↓
Global Permission
        ↓
BotAccess
        ↓
Resource ownership / Bot relation
        ↓
Operation allowed
```

Нельзя считать наличие одного из этих условий достаточным, если бизнес-правила требуют остальные.

---

# Инварианты

Всегда должны соблюдаться следующие правила:

* User и Person являются разными понятиями;
* глобальные permissions и BotAccess являются независимыми уровнями авторизации;
* User без доступа к Bot не должен видеть его обычными средствами административной панели;
* дочерний ресурс не должен обходить проверку доступа к родительскому Bot;
* MoonShine не является источником бизнес-логики;
* административные действия должны использовать Application/Domain;
* исторические данные не изменяются через обычное редактирование административной панели;
* критические изменения должны быть доступны для аудита.
