# Broadcasts

**Документ:** `docs/admin/broadcasts.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

Настоящий документ описывает административное управление `Broadcast` внутри выбранного `Bot`.

Бизнес-модель Broadcast описана в:

`docs/domain/broadcast.md`

Настоящий документ определяет только административные сценарии: просмотр, создание, редактирование, настройку аудитории, локализацию, планирование, запуск, отмену и просмотр результатов рассылки.

---

# Контекст Bot

Все операции с Broadcast выполняются в контексте конкретного Bot.

```text
MVBotsHub
    ↓
Bot
    ↓
Broadcasts
```

Перед любой операцией проверяются:

```text
User authenticated
        ↓
Global Permission
        ↓
BotAccess
        ↓
Broadcast Permission
        ↓
Broadcast belongs to Bot
```

Прямой доступ к Broadcast по URL или внутреннему `id` не должен обходить проверку доступа к Bot.

---

# Список Broadcast

В списке отображаются только рассылки выбранного Bot, доступные текущему User.

Для каждой записи могут отображаться:

* название;
* `code`;
* статус;
* время запуска или планирования;
* размер аудитории;
* прогресс выполнения;
* дата последнего изменения;
* User, создавший Broadcast.

---

# Фильтрация

Список должен поддерживать фильтрацию как минимум по:

```text
status
code
name
scheduled_at
created_by
```

Фильтрация выполняется сервером.

---

# Создание Broadcast

Создание выполняется через Application Use Case.

```text
MoonShine
   ↓
CreateBroadcast
   ↓
Broadcast
```

После создания Broadcast находится в состоянии `Draft`.

На этапе Draft пользователь может подготовить содержимое и аудиторию без фактической отправки сообщений.

---

# Редактирование Draft

Пока Broadcast находится в `Draft`, пользователь с permission `broadcast.update` может изменять:

* название;
* содержимое;
* локализацию;
* аудиторию;
* расписание;
* другие разрешённые настройки.

Изменения выполняются через Application Use Case.

---

# Локализация

Переводы содержимого Broadcast редактируются непосредственно в форме Broadcast.

Например:

```text
Основной текст:
Новая акция!

English:
New promotion!

Қазақша:
Жаңа акция!
```

Отдельный переход в глобальный раздел Localization не требуется.

Подробные правила:

`docs/domain/localization.md`

---

# Аудитория

Пользователь должен иметь возможность определить, кто получит Broadcast.

Аудитория может строиться на основании:

* всех активных BotMember;
* фильтров;
* сегментов;
* языка;
* статуса участника;
* пользовательских переменных;
* других доступных критериев.

Формирование аудитории должно выполняться в серверной части.

---

# Предварительный просмотр аудитории

До запуска желательно предоставлять предварительный результат:

```text
Подходят: 12 540
Исключено: 183
```

Предварительный расчёт не считается окончательной исторической фиксацией аудитории.

---

# Фиксация аудитории

Перед фактическим началом выполнения система должна определить набор получателей, относящийся к конкретному запуску Broadcast.

После начала выполнения изменение исходных фильтров не должно задним числом изменять уже запущенную рассылку.

История должна позволять определить:

```text
кто был выбран
кто получил
кто был пропущен
кто получил ошибку
```

---

# Планирование

Broadcast может быть:

```text
Отправить сейчас
```

или:

```text
Запланировать
```

Для запланированной рассылки задаётся `scheduled_at`.

Пользователь должен иметь возможность видеть:

* дату;
* время;
* часовой пояс, в котором интерпретируется расписание.

---

# Проверка перед запуском

Перед переводом Broadcast в `Scheduled` или `Running` система должна проверить как минимум:

* наличие содержимого;
* корректность аудитории;
* доступность Bot;
* допустимость выбранных настроек;
* корректность локализации согласно политике Bot;
* наличие необходимых ресурсов;
* отсутствие запрещённых конфликтов состояния.

Критическая ошибка блокирует запуск.

---

# Запуск сейчас

При запуске без расписания Broadcast переходит из `Draft` в `Running` через соответствующий Application Use Case.

```text
Draft
  ↓
Validation
  ↓
StartBroadcast
  ↓
Running
```

Фактическая отправка выполняется асинхронно.

---

# Планируемая рассылка

Для запланированной рассылки:

```text
Draft
  ↓
Validation
  ↓
Scheduled
```

В момент наступления `scheduled_at` Application/Queue переводит рассылку в `Running`, если Bot и Broadcast всё ещё доступны для запуска.

---

# Отправка

Broadcast не взаимодействует с Telegram напрямую.

Общая схема:

```text
Broadcast
    ↓
Application
    ↓
Queue
    ↓
Delivery Jobs
    ↓
Transport Gateway
    ↓
Telegram / другой канал
```

Transport-specific логика находится вне Domain.

---

# Прогресс

Во время `Running` административный интерфейс должен показывать прогресс рассылки.

Например:

```text
Всего:       12 540
Отправлено:  11 200
Ошибки:         180
Пропущено:      120
Осталось:     1 040

Прогресс: 89%
```

Значения рассчитываются на основе фактических операций доставки.

---

# Результаты доставки

Для каждого получателя могут существовать состояния:

```text
Pending
Sent
Failed
Skipped
Cancelled
```

История результатов должна быть доступна в рамках соответствующих permissions.

---

# Повторные попытки

Временная ошибка доставки одному получателю не должна останавливать весь Broadcast.

Application/Infrastructure могут выполнять retry с backoff.

Например:

```text
Recipient A → Sent
Recipient B → Failed → Retry
Recipient C → Sent
```

Количество и стратегия retry определяются техническим слоем.

---

# Идемпотентность

Повторный запуск Job не должен приводить к повторной отправке одного и того же логического сообщения одному и тому же BotMember.

Система должна иметь уникальный контекст операции доставки.

Административный интерфейс не должен создавать дубликаты операций при повторной отправке формы или обновлении страницы.

---

# Отмена

Broadcast может быть отменён до завершения.

Допустимые состояния для отмены определяются жизненным циклом Broadcast.

При отмене:

* новые операции доставки не создаются;
* уже отправленные сообщения не отменяются;
* результаты уже выполненных операций сохраняются.

---

# Завершение

Broadcast переводится в `Completed`, когда все операции, относящиеся к запуску, находятся в конечном состоянии.

Например:

```text
Sent
Failed
Skipped
Cancelled
```

Незавершённые операции не должны оставаться `Pending` при установке финального состояния.

---

# Ошибки

Если критическая системная ошибка делает нормальное завершение невозможным, Broadcast переводится в `Failed`.

Административный интерфейс должен отображать причину в безопасной форме.

Технические детали не должны раскрывать секреты или чувствительные данные.

---

# История

История выполнения Broadcast является неизменяемой.

После фиксации результата доставки обычное редактирование не должно переписывать исторические факты.

Административная панель может предоставлять просмотр и фильтрацию истории, но не произвольное изменение результатов прошлых операций.

---

# Повторный запуск

Завершённый Broadcast не должен повторно переходить в `Running` напрямую.

Если необходимо выполнить аналогичную рассылку ещё раз, создаётся новый Broadcast или используется отдельный механизм повторного запуска, который создаёт новую операцию и сохраняет историю предыдущего запуска.

---

# Удаление

Удаление Broadcast означает Soft Delete.

После удаления:

* Broadcast скрывается из обычных списков;
* новые операции запрещаются;
* история выполнения сохраняется;
* результаты доставки сохраняются.

Физическое удаление не выполняется в обычном административном процессе.

---

# Права доступа

Основные permissions:

```text
broadcast.view
broadcast.create
broadcast.update
broadcast.send
broadcast.cancel
broadcast.delete
broadcast.results.view
broadcast.export
```

`broadcast.update` не должен автоматически давать право `broadcast.send`.

Это позволяет разделить подготовку рассылки и право на её фактический запуск.

---

# Доступ к аудитории

Операции, позволяющие экспортировать или просматривать состав аудитории, должны учитывать отдельные ограничения безопасности.

Например, право:

```text
broadcast.results.view
```

не обязательно должно автоматически давать право выгружать персональные данные всех получателей.

---

# Аудит

Критические операции Broadcast должны фиксироваться в административном аудите.

Например:

```text
Broadcast created
Audience changed
Broadcast scheduled
Broadcast started
Broadcast cancelled
Broadcast completed
Broadcast failed
Broadcast deleted
```

Минимально должны фиксироваться:

```text
User
Bot
Broadcast
Operation
Date / Time
Result
```

---

# Notifications

Административные Notification могут использоваться для информирования User о результатах фоновых операций.

Например:

```text
Broadcast completed
Broadcast failed
Scheduled broadcast started
```

Notification не заменяет аудит и историю Broadcast.

---

# Безопасность

Каждая административная операция должна проходить серверную проверку:

```text
Authenticated User
        ↓
Global Permission
        ↓
BotAccess
        ↓
Broadcast Permission
        ↓
Broadcast belongs to Bot
        ↓
Execute
```

Скрытие действия в MoonShine не является достаточной защитой.

---

# Инварианты

Всегда должны соблюдаться следующие правила:

* User работает только с Broadcast доступного ему Bot;
* Broadcast не отправляет сообщения напрямую;
* `broadcast.update` и `broadcast.send` являются отдельными правами;
* после начала выполнения содержимое и аудитория не должны незаметно изменяться задним числом;
* история операций доставки сохраняется;
* завершённый Broadcast не запускается повторно напрямую;
* удаление является Soft Delete;
* повторная обработка Job не приводит к дубликату доставки;
* административный UI не является единственным уровнем безопасности.
