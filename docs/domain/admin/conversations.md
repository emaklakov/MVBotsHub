# Conversations

**Документ:** `docs/admin/conversations.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

Настоящий документ описывает административный просмотр и работу с `Conversation` внутри выбранного `Bot`.

Бизнес-модель Conversation описана в:

`docs/domain/conversation.md`

История сообщений описана в:

`docs/domain/message.md`

Административная подсистема предоставляет доступ к Conversation только в пределах прав текущего `User`.

---

# Контекст Bot

Все операции выполняются в контексте конкретного Bot.

```text
MVBotsHub
    ↓
Bot
    ↓
Conversations
```

Перед доступом проверяется:

```text
Authenticated User
        ↓
Global Permission
        ↓
BotAccess
        ↓
Conversation Permission
        ↓
Conversation belongs to Bot
        ↓
Allow
```

Прямой URL или внутренний `id` Conversation не должен позволять обойти проверку доступа к Bot.

---

# Список Conversation

В списке отображаются Conversation выбранного Bot, доступные текущему User.

Для каждой записи могут отображаться:

* BotMember;
* Person, если разрешён доступ к персональным данным;
* статус Conversation;
* дата начала;
* дата последней активности;
* дата завершения;
* причина завершения;
* количество Message;
* активная FlowSession, если существует.

---

# Фильтрация

Минимально рекомендуется поддерживать фильтры:

```text
status
created_at
last_activity_at
closed_at
close_reason
bot_member
```

Для поиска по человеку могут использоваться разрешённые поля Person, например телефон или имя, с учётом privacy policy.

Фильтрация должна выполняться на серверной стороне.

---

# Открытие Conversation

При открытии Conversation пользователь получает исторический контекст:

```text
Conversation
   │
   ├── BotMember
   ├── Person
   ├── Status
   ├── FlowSession
   └── Messages
```

Доступ к каждому связанному объекту должен соответствовать правам User.

---

# История Message

История сообщений отображается в хронологическом порядке.

```text
Message 1
Message 2
Message 3
...
```

Для больших Conversation используется постраничная или ленивую загрузку.

Вся история не должна загружаться в память одним запросом.

---

# Неизменяемость истории

Административная панель не предоставляет обычного редактирования исторических Message.

Нельзя задним числом изменять:

* текст сообщения;
* направление;
* время;
* источник;
* внешний идентификатор;
* исторический результат доставки.

Это является частью принципа `Immutable History`.

---

# Ответ на сообщение

Если в будущем административная подсистема поддерживает ответ оператора пользователю, это не должно изменять существующий Message.

Вместо этого создаётся новое Outgoing Message.

```text
Message пользователя
       ↓
Ответ оператора
       ↓
New Message
```

---

# Оператор и Live Chat

Архитектура допускает будущий режим Live Chat.

В этом случае Conversation может быть передан оператору, имеющему permission работы с Conversation.

```text
Conversation
   ↓
Assign Operator
   ↓
User
```

Назначение оператора не изменяет исторические Message.

---

# FlowSession

При открытии Conversation административный интерфейс может показывать текущую FlowSession.

Например:

```text
Flow: registration
Version: registration@7
Node: ask-phone
Status: Waiting
```

Эта информация является диагностической и не означает, что администратор может произвольно изменять состояние FlowSession.

---

# Управление FlowSession

Операции с FlowSession должны быть доступны только через отдельные permissions и предусмотренные Application Use Cases.

Например, в будущем:

```text
conversation.flow.pause
conversation.flow.resume
conversation.flow.cancel
```

Обычный просмотр Conversation не предоставляет автоматически право управлять выполнением Flow.

---

# Завершение Conversation

Если бизнес-правила разрешают ручное завершение Conversation, используется отдельная операция.

```text
Close Conversation
```

При этом обязательно фиксируется причина завершения, например:

```text
Administrator
```

Исторические Message не изменяются.

---

# Автоматическое закрытие

Conversation автоматически закрывается после **30 календарных дней** отсутствия активности в соответствии с доменными правилами.

Причина:

```text
Inactivity
```

Административный интерфейс должен показывать эту причину отдельно от ручного завершения.

---

# Повторное открытие

Завершённый Conversation не должен просто переводиться обратно в `Active` как обычная операция.

Если после закрытия пользователь снова пишет через установленный период, создаётся новый Conversation.

Это сохраняет модель Conversation как отдельного сеанса общения.

---

# Персональные данные

Conversation может содержать персональные данные Person и BotMember.

Доступ к ним должен контролироваться отдельно от общего права просмотра Conversation, если политика безопасности предусматривает такое разделение.

Например:

```text
conversation.view
person.view
```

User с правом просмотра Conversation, но без права просмотра персональных данных, должен видеть обезличенное представление там, где это требуется политикой системы.

---

# Экспорт

Если предусмотрен экспорт истории Conversation, для него должно требоваться отдельное permission, например:

```text
conversation.export
```

Экспорт должен учитывать:

* BotAccess;
* доступ к персональным данным;
* правила хранения данных;
* аудит операции.

---

# Удаление

Conversation не удаляется физически в обычном административном процессе.

Административная панель не должна предоставлять кнопку физического удаления исторического Conversation.

При необходимости применяется политика анонимизации или отдельная политика удаления данных, согласованная с правилами хранения проекта.

---

# Аудит

Критические действия с Conversation должны фиксироваться в административном аудите.

Например:

```text
Conversation viewed
Conversation exported
Conversation closed
Operator assigned
FlowSession changed
```

Просмотр каждого отдельного Conversation может также аудироваться, если это требуется политикой безопасности.

---

# Права доступа

Основные permissions могут включать:

```text
conversation.view
conversation.export
conversation.close
conversation.manage
conversation.operator.assign
```

Права должны разделяться по принципу минимально необходимых полномочий.

---

# Безопасность

Проверка должна выполняться на серверной стороне:

```text
Authenticated User
        ↓
Global Permission
        ↓
BotAccess
        ↓
Conversation Permission
        ↓
Resource belongs to Bot
        ↓
Privacy checks
        ↓
Allow
```

Скрытие Conversation в интерфейсе не является механизмом безопасности.

---

# Инварианты

Всегда должны соблюдаться следующие правила:

* User видит только Conversation доступного ему Bot;
* исторические Message не редактируются;
* Conversation не удаляется физически в обычном процессе;
* закрытый Conversation не превращается обратно в тот же активный сеанс из-за нового сообщения;
* ручное завершение фиксирует причину `Administrator` или соответствующую причину;
* автоматическое завершение после 30 дней фиксирует `Inactivity`;
* доступ к персональным данным может быть ограничен отдельно;
* экспорт требует отдельного разрешения;
* UI не является единственным уровнем безопасности.

---

# Будущие возможности

Архитектура административного интерфейса допускает:

* Live Chat;
* назначение операторов;
* внутренние заметки;
* теги Conversation;
* поиск по истории;
* AI-подсказки оператору;
* оценку качества обслуживания;
* SLA и статусы обработки.
