# Audit

**Документ:** `docs/admin/audit.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

`Audit` описывает административный аудит действий пользователей MVBotsHub.

Аудит предназначен для фиксации значимых действий в административной подсистеме и позволяет определить:

```text
кто
что сделал
над каким объектом
когда
из какого контекста
с каким результатом
```

Аудит не является частью бизнес-логики конкретного `Bot`, `Flow` или `Broadcast`.

---

# Ответственность

Аудит отвечает за фиксацию административных фактов, которые важны для:

* безопасности;
* расследования изменений;
* контроля действий User;
* соответствия внутренним политикам;
* диагностики спорных операций.

Аудит не отвечает за:

* выполнение бизнес-операции;
* авторизацию;
* хранение состояния Flow;
* историю Telegram-сообщений;
* историю Conversation.

---

# Основной принцип

Аудит создаётся как следствие выполненного административного действия.

```text
User
  ↓
Application Use Case
  ↓
Business Operation
  ↓
Audit Record
```

Аудит не должен быть единственным местом, где хранится состояние операции.

---

# Что подлежит аудиту

Аудиту подлежат прежде всего операции, которые:

* изменяют права доступа;
* изменяют состояние Bot;
* изменяют Flow;
* публикуют FlowVersion;
* запускают или отменяют Broadcast;
* изменяют административные настройки;
* изменяют данные безопасности;
* экспортируют чувствительные данные;
* выполняют другие критически важные действия.

Не каждое чтение обязательно должно записываться в аудит.

Просмотр чувствительных данных может дополнительно аудироваться политикой безопасности.

---

# Примеры событий

Например:

```text
UserLoggedIn
UserBlocked
BotCreated
BotUpdated
BotArchived
BotRestored
BotAccessGranted
BotAccessUpdated
BotAccessRevoked
FlowCreated
FlowPublished
FlowArchived
FlowRestored
BroadcastCreated
BroadcastStarted
BroadcastCancelled
BotSettingsUpdated
MemberPreferencesUpdated
ConversationExported
MemberDataExported
```

Конкретный набор событий может расширяться.

---

# Основные свойства Audit Record

| Поле          | Описание                                                     |
| ------------- | ------------------------------------------------------------ |
| id            | Уникальный идентификатор записи аудита                       |
| actor_user_id | User, выполнивший действие                                   |
| action        | Код действия                                                 |
| resource_type | Тип изменённого объекта                                      |
| resource_id   | Внутренний идентификатор объекта, если применимо             |
| bot_id        | Bot, в контексте которого выполнено действие, если применимо |
| result        | Результат операции                                           |
| metadata      | Дополнительные безопасные данные                             |
| occurred_at   | Время события                                                |
|               |                                                              |

Дополнительные поля могут использоваться для корреляции событий и диагностики.

---

# Actor

`actor_user_id` указывает User, от имени которого выполнена административная операция.

Для системных операций, которые не инициированы непосредственно User, может использоваться специальный системный источник:

```text
System
```

Системные действия должны быть явно отличимы от действий User.

---

# Action

`action` является стабильным техническим идентификатором действия.

Примеры:

```text
bot.create
bot.update
bot.archive
bot.restore
bot-access.grant
bot-access.revoke
flow.publish
broadcast.send
conversation.export
```

Название действия не должно зависеть от текста административного интерфейса.

---

# Resource

Audit Record должен позволять определить объект, над которым выполнено действие.

Например:

```text
resource_type = Flow
resource_id = 125
```

При необходимости дополнительно сохраняется:

```text
bot_id = 10
```

Внутренние идентификаторы могут использоваться в аудите, поскольку аудит является внутренним системным журналом, а не публичным API.

---

# Public Code

Если объект имеет публичный `code`, его также можно сохранять в безопасных metadata для удобства диагностики.

Например:

```json
{
    "code": "checkout"
}
```

Это не заменяет внутреннюю связь по ID.

---

# Result

Результат аудируемого действия должен быть явно определён.

Например:

```text
Success
Failure
Denied
Cancelled
```

Неуспешная попытка выполнения критической операции может также аудироваться, если она важна для безопасности.

---

# Metadata

`metadata` содержит только дополнительные данные, необходимые для анализа события.

Например:

```json
{
    "old_role": "Operator",
    "new_role": "Administrator"
}
```

Metadata не должно содержать:

* пароли;
* access tokens;
* API keys;
* полные секреты внешних интеграций;
* лишние персональные данные.

---

# Изменения значений

Для критических изменений может фиксироваться:

```text
old value
new value
```

Но только для тех полей, которые разрешено хранить в аудите.

Например, допустимо:

```text
old_role = Operator
new_role = Administrator
```

Но не следует записывать секретное значение credential целиком.

---

# Неизменяемость

Audit Record является исторической записью.

После фиксации запись не редактируется обычными административными средствами.

Историю аудита нельзя использовать как обычную таблицу настроек.

---

# Удаление

Audit Record не удаляется в обычном административном процессе.

Очистка или архивирование аудита выполняются только в рамках отдельной политики хранения данных.

Такая политика должна учитывать требования безопасности, бизнеса и законодательства, применимые к проекту.

---

# Просмотр аудита

Пользователь должен видеть только те записи аудита, доступ к которым разрешён его permissions.

Минимально возможны permissions:

```text
audit.view
audit.export
```

Системный аудит может быть доступен только администраторам с повышенными полномочиями.

---

# Фильтрация

Административный интерфейс должен поддерживать поиск и фильтрацию по:

```text
User
action
resource_type
Bot
result
date range
```

Фильтрация выполняется на серверной стороне.

---

# Контекст Bot

Если событие относится к конкретному Bot, Audit Record должен содержать контекст Bot.

Например:

```text
User A
    ↓
Bot Support
    ↓
flow.publish
    ↓
checkout@7
```

Это позволяет анализировать действия пользователя в рамках конкретного Bot.

---

# Аудит доступа

Особенно важны операции:

```text
bot-access.grant
bot-access.update
bot-access.revoke
```

В таких событиях рекомендуется фиксировать:

```text
Actor User
Target User
Bot
Old Role
New Role
Date / Time
```

---

# Аудит Flow

Для Flow критическими являются:

```text
flow.create
flow.update
flow.publish
flow.disable
flow.archive
flow.restore
flow.delete
```

При публикации желательно фиксировать:

```text
User
Bot
Flow
Version
Public Version Identifier
Date / Time
```

Например:

```text
checkout@7
```

---

# Аудит Broadcast

Для Broadcast критическими являются:

```text
broadcast.create
broadcast.update
broadcast.schedule
broadcast.send
broadcast.cancel
broadcast.delete
```

Особенно важно фиксировать User, инициировавшего фактический запуск массовой рассылки.

---

# Аудит экспорта данных

Экспорт потенциально чувствительных данных должен аудироваться отдельно.

Например:

```text
conversation.export
member.export
```

В событии достаточно зафиксировать факт и контекст операции.

Содержимое экспортируемого файла не должно записываться в Audit Record.

---

# Отказ в доступе

В зависимости от политики безопасности могут аудироваться не только успешные действия, но и критические отказы в авторизации.

Например:

```text
authorization.denied
```

Это позволяет выявлять подозрительные попытки доступа к Bot или административным ресурсам.

---

# Связь с UserLog

`UserLog` является частью текущей модели административного пользователя и может хранить технические записи, связанные с User.

Audit не должен превращаться в дубликат всех UserLog.

Принцип разделения:

```text
UserLog
→ техническая история User

Audit
→ значимые административные действия системы
```

Конкретное распределение событий между этими механизмами определяется административной подсистемой.

---

# Безопасность

Доступ к Audit является чувствительной административной возможностью.

Поэтому:

* Audit нельзя показывать обычному User без permission;
* экспорт Audit требует отдельного permission;
* секретные данные не должны попадать в metadata;
* аудит не должен позволять обходить обычные ограничения доступа к Bot.

---

# Производительность

Аудит может генерировать большое количество записей.

Хранилище должно поддерживать:

* индексацию по actor_user_id;
* индексацию по bot_id;
* индексацию по action;
* фильтрацию по времени;
* постраничное чтение.

Конкретные индексы и стратегию хранения определяет Infrastructure.

---

# Инварианты

Всегда должны соблюдаться следующие правила:

* Audit Record является исторической записью;
* обычное администрирование не изменяет уже созданный Audit Record;
* критические действия должны быть аудируемыми;
* аудит не хранит секреты;
* User и System должны быть различимы как источник действия;
* доступ к аудиту сам контролируется permissions;
* запись аудита не является заменой бизнес-данных;
* отсутствие Audit Record не должно означать отсутствие самого бизнес-события.

---

# Будущие возможности

Архитектура допускает:

* расширенный audit trail;
* корреляцию связанных действий;
* трассировку фоновых операций;
* интеграцию с SIEM;
* алерты по подозрительным действиям;
* политики хранения;
* автоматическое архивирование старых записей.
