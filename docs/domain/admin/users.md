# User

**Документ:** `docs/admin/users.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

`User` представляет пользователя административной подсистемы MVBotsHub.

User — это сотрудник или другой пользователь, которому предоставлен доступ к управлению платформой.

User не является `Person` и не является `BotMember`.

---

# Модель User

User является собственной моделью приложения.

Текущая физическая реализация находится в:

```text
App\Models\User\User
```

Модель User является частью административной подсистемы и может иметь связанные модели:

```text
App\Models\User\
├── User
├── Role
├── Permission
├── Session
├── UserLog
├── UserSetting
└── Notification
```

Физическая структура моделей не изменяет бизнес-разделение между User и Person.

---

# Ответственность

User отвечает за идентификацию и работу пользователя в административной части MVBotsHub.

User может:

* входить в административную панель;
* иметь глобальные роли и permissions;
* иметь доступ к конкретным Bot через BotAccess;
* выполнять разрешённые административные операции;
* иметь собственные настройки административного интерфейса.

User не отвечает за:

* идентификацию Person;
* участие человека в Bot;
* историю Conversation;
* выполнение Flow;
* хранение BotMember.

---

# User и Person

Это разные сущности с разными задачами.

```text
User
 │
 └── управляет MVBotsHub

Person
 │
 └── взаимодействует с Bot
```

Наличие записи Person не создаёт User автоматически.

Наличие User не означает наличие Person.

Эти сущности не должны объединяться только на основании похожих персональных данных.

---

# Аутентификация

User проходит аутентификацию для доступа к административной подсистеме.

Механизм аутентификации является технической ответственностью Application/Infrastructure и не должен смешиваться с доменной моделью Bot или Person.

После успешной аутентификации система устанавливает текущего User, относительно которого выполняются проверки глобальных permissions и BotAccess.

---

# Авторизация

Авторизация User выполняется на двух уровнях.

## Глобальный уровень

Определяет доступ к функциям MVBotsHub независимо от конкретного Bot.

Например:

```text
user.view
user.manage
bot.create
system.settings.view
```

---

## Уровень Bot

Определяет возможность выполнять операцию с конкретным Bot.

Проверка учитывает:

```text
User
  +
Global Permission
  +
BotAccess
  +
Bot-level Permission
```

Один глобальный permission не должен автоматически давать доступ ко всем Bot, если соответствующая политика не предусматривает обратное.

---

# BotAccess

Связь User с конкретным Bot осуществляется через `BotAccess`.

Например:

```text
User
 │
 ├── Bot A → Owner
 ├── Bot B → Operator
 └── Bot C → Analyst
```

Подробнее:

`docs/domain/bot-access.md`

---

# Видимость Bot

По умолчанию User видит в административной панели только:

* Bot, которые он создал;
* Bot, к которым ему предоставлен действующий BotAccess.

Специальные глобальные permissions могут предоставлять расширенный доступ, например системному администратору.

Ограничение видимости должно применяться не только к списку Bot, но и к отдельным ресурсам этих Bot.

---

# Создание User

Создание User выполняется через административный Application Use Case.

При создании должны быть определены как минимум:

* идентификация User;
* состояние User;
* набор начальных ролей или permissions, если они предусмотрены политикой;
* параметры, необходимые для последующей аутентификации.

Создание User не должно автоматически предоставлять доступ ко всем Bot.

---

# Статус User

User может иметь состояние, определяющее возможность входа и выполнения административных операций.

Например:

```text
Active
Blocked
Archived
```

Blocked User не должен проходить успешную административную авторизацию.

Архивация используется для пользователей, выведенных из эксплуатации, когда требуется сохранить историю их действий.

---

# Роли

Роль определяет набор permissions User.

Роли могут применяться:

* глобально;
* в контексте конкретного Bot через BotAccess.

Конкретная модель RBAC относится к административной подсистеме и может использовать существующий механизм приложения.

---

# Permissions

Permission представляет отдельное разрешение на выполнение операции.

Например:

```text
user.view
user.manage
bot.create
bot.update
flow.publish
broadcast.send
conversation.view
```

Названия permissions должны быть однозначными и отражать конкретное право.

---

# Сессии

Административные сессии User являются технической частью авторизации.

Они могут использоваться для:

* контроля активных входов;
* отзыва сессий;
* аудита;
* определения активности User.

Сессия не является частью Domain Bot.

---

# UserLog

`UserLog` предназначен для технического или административного аудита действий User.

Например:

```text
вход
выход
неудачная аутентификация
создание Bot
выдача BotAccess
публикация Flow
запуск Broadcast
```

История UserLog не должна зависеть от конкретного интерфейса MoonShine.

---

# UserSetting

`UserSetting` содержит индивидуальные настройки административного интерфейса User.

Например:

* настройки отображения;
* предпочтения интерфейса;
* параметры рабочего пространства;
* другие настройки, относящиеся именно к административному пользователю.

UserSetting не используется для хранения настроек Bot или BotMember.

---

# Notification

`Notification` содержит административные уведомления User.

Например:

* завершение фоновой операции;
* результат публикации Flow;
* ошибка импорта;
* завершение Broadcast;
* системное уведомление.

Notification не является Telegram-сообщением Bot.

---

# Удаление User

User не должен физически удаляться в обычном административном процессе, если это приводит к потере аудита.

Предпочтительно использовать блокировку или архивирование, сохраняя историю действий.

Особые операции физического удаления должны выполняться только в рамках отдельной политики хранения данных.

---

# Аудит

Критические действия User должны быть доступны для аудита.

Минимально должны фиксироваться:

* кто выполнил действие;
* когда выполнено действие;
* над каким Bot или ресурсом выполнено действие;
* какой тип операции выполнен;
* результат операции.

---

# Безопасность

Все административные операции должны выполняться в контексте аутентифицированного User.

Для операций с Bot необходимо дополнительно проверять BotAccess.

Нельзя считать скрытие элемента UI достаточной защитой.

Проверка доступа должна выполняться на серверной стороне Application/Presentation Boundary.

Прямой доступ к URL, API или идентификатору ресурса не должен позволять обойти авторизацию.

---

# Инварианты

Всегда должны соблюдаться следующие правила:

* User является пользователем административной подсистемы;
* User и Person — разные сущности;
* User без соответствующего доступа не может работать с Bot;
* глобальные permissions и BotAccess проверяются независимо;
* создание User не предоставляет автоматически доступ ко всем Bot;
* Blocked User не может выполнять административные операции;
* история критических действий сохраняется для аудита;
* UserSetting не используется для хранения Bot или BotMember настроек;
* Notification не является сообщением Telegram Bot.
