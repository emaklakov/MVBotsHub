# Sessions

**Документ:** `docs/admin/sessions.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

`Session` представляет административную сессию аутентифицированного `User` в MVBotsHub.

Сессия используется для управления доступом к административной части системы и позволяет контролировать активные входы пользователя.

`Session` не является `Conversation` и не имеет отношения к пользовательской сессии общения с Bot.

---

# Ответственность

Session отвечает за:

* фиксацию активной административной сессии;
* связь с User;
* идентификацию текущего входа;
* время создания и последней активности;
* время завершения или отзыва сессии;
* технические признаки устройства и окружения, если они необходимы для безопасности.

Session не отвечает за:

* глобальные permissions;
* BotAccess;
* состояние BotMember;
* выполнение Flow;
* Conversation;
* Telegram API;
* бизнес-операции Bot.

---

# Принадлежность

Каждая Session принадлежит одному `User`.

```text
User
 │
 ├── Session
 ├── Session
 └── ...
```

Один User может иметь несколько активных сессий, если политика безопасности это разрешает.

---

# Основные свойства

На концептуальном уровне Session может содержать:

| Свойство         | Назначение                                                       |
| ---------------- | ---------------------------------------------------------------- |
| id               | Внутренний идентификатор                                         |
| user_id          | Владелец сессии                                                  |
| token_identifier | Идентификатор сессии/токена без хранения секрета в открытом виде |
| ip_address       | IP-адрес входа, если хранение разрешено политикой безопасности   |
| user_agent       | User-Agent, если требуется для аудита и безопасности             |
| last_activity_at | Последняя активность                                             |
| expires_at       | Время истечения                                                  |
| revoked_at       | Время отзыва                                                     |
| created_at       | Время создания                                                   |

Конкретный состав полей определяется реализацией аутентификации.

---

# Аутентификация

После успешной аутентификации User создаётся Session.

Общий поток:

```text
Credentials
    ↓
Authentication
    ↓
User
    ↓
Session
    ↓
Authenticated Request
```

Session подтверждает текущий административный контекст пользователя, но сама по себе не определяет его permissions.

---

# Авторизация

Каждый административный запрос сначала связывается с User через действующую Session, после чего выполняется авторизация:

```text
Session
   ↓
User
   ↓
Global Permission
   ↓
BotAccess
   ↓
Operation Permission
```

Session не заменяет Authorization.

---

# Состояния Session

Концептуально Session может находиться в состояниях:

```text
Active
Expired
Revoked
```

## Active

Сессия действительна и может использоваться для аутентифицированных запросов.

## Expired

Срок действия завершён.

Сессия больше не может использоваться для входа в административную часть.

## Revoked

Сессия досрочно отозвана пользователем или системой.

---

# Завершение сессии

При обычном выходе User текущая Session переводится в завершённое или отозванное состояние в соответствии с механизмом аутентификации.

Другие активные Session могут продолжать работать, если пользователь не выбрал операцию выхода со всех устройств.

---

# Отзыв одной Session

User с соответствующим правом может завершить отдельную активную Session.

Например:

```text
Устройства

MacBook
Active

Chrome
Active

Mobile
Active

→ Завершить Mobile
```

После отзыва Session следующий запрос с неё должен быть отклонён.

---

# Отзыв всех Session

Система должна поддерживать операцию:

```text
Logout from all devices
```

При её выполнении все активные Session User отзываются, кроме текущей, если интерфейс явно не предусматривает иное поведение.

---

# Блокировка User

При блокировке User все его активные административные Session должны быть отозваны или иным способом немедленно признаны недействительными.

```text
User blocked
    ↓
Revoke active sessions
```

Это является обязательной частью безопасной блокировки административного пользователя.

---

# Изменение критических данных User

После изменения критических параметров безопасности User система может потребовать отзыв активных Session.

Например:

* сброс пароля;
* изменение MFA;
* изменение критических способов аутентификации.

Конкретная политика определяется механизмом Authentication.

---

# Хранение токенов

Session не должна хранить секреты аутентификации в открытом виде, если механизм токенов позволяет использовать безопасное представление.

В базе рекомендуется хранить только данные, необходимые для проверки и отзыва Session.

Конкретная криптографическая реализация относится к Infrastructure.

---

# Административный просмотр Session

Пользователь с соответствующим permission может просматривать собственные Session.

Например:

```text
session.view.own
```

Системный администратор при наличии соответствующего permission может просматривать Session других User.

Например:

```text
session.view
```

Просмотр чужих Session должен быть ограничен повышенными правами.

---

# Права доступа

Минимальный набор permissions может включать:

```text
session.view
session.revoke
session.revoke-all
session.view-own
```

Конкретные имена могут уточняться общей системой permissions.

---

# Аудит

Следующие события могут фиксироваться в Audit/UserLog:

```text
login.success
login.failed
session.created
session.revoked
session.expired
logout
logout.all
```

Особенно важны:

* успешный вход;
* неудачные попытки;
* отзыв Session;
* массовый отзыв Session;
* блокировка User.

---

# Уведомления

При подозрительных или значимых событиях система может создавать Notification.

Например:

```text
Новый вход в административную панель

Устройство: Chrome
Время: ...
```

Notification не является заменой Audit или Session.

---

# Безопасность

Session является чувствительным объектом безопасности.

Поэтому:

* нельзя показывать секреты токенов;
* нельзя позволять User изменять Session другого User без соответствующего permission;
* отзыв Session должен выполняться сервером;
* UI не является единственным уровнем защиты;
* заблокированный User не должен продолжать использовать действующие Session.

---

# Жизненный цикл

Типичный жизненный цикл:

```text
Created
   ↓
Active
   ↓
Expired / Revoked
```

История завершённых Session может сохраняться для аудита и анализа безопасности.

---

# Удаление

Session не обязательно хранить бессрочно.

Удаление старых завершённых Session выполняется по отдельной политике хранения безопасности.

Удаление Session не должно нарушать Audit и историю значимых событий User.

---

# Производительность

Проверка Session выполняется часто, поэтому доступ к активным Session должен быть быстрым.

Допускается использование Cache для ускорения проверки, если это соответствует используемому механизму аутентификации.

Cache не является источником истины.

---

# Инварианты

Всегда должны соблюдаться следующие правила:

* Session принадлежит одному User;
* Session не определяет permissions;
* Session не определяет BotAccess;
* Expired и Revoked Session не могут использоваться для административных запросов;
* блокировка User инвалидирует его активные Session;
* секреты Session не раскрываются через административный интерфейс;
* отзыв Session не изменяет исторические данные User;
* Session не является Conversation.

---

# Будущие возможности

Архитектура допускает:

* MFA;
* доверенные устройства;
* управление активными устройствами;
* географические аномалии входа;
* уведомления о подозрительной активности;
* автоматический отзыв Session при изменении политики безопасности;
* device fingerprinting в рамках допустимой privacy policy.
