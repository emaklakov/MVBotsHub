# Roles

**Документ:** `docs/admin/roles.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

`Role` объединяет набор `Permission` и используется для управления полномочиями `User` в административной подсистеме MVBotsHub.

Role отвечает на вопрос:

> Какие операции доступны User?

Role не определяет, с каким `Bot` User может работать. Для этого используется `BotAccess`.

---

# Ответственность

Role отвечает за:

* группировку permissions;
* назначение стандартного набора полномочий;
* отображение состава полномочий;
* управление изменениями ролей в рамках RBAC.

Role не отвечает за:

* аутентификацию User;
* доступ к конкретному Bot;
* состояние Bot;
* бизнес-логику Flow;
* выполнение Broadcast;
* работу Telegram API.

---

# Связь с User

User может иметь одну или несколько ролей в зависимости от модели RBAC приложения.

```text
User
 ├── Role
 ├── Role
 └── ...
```

Роль предоставляет User набор permissions.

---

# Связь с BotAccess

Роли могут применяться на разных уровнях.

```text
User
 ├── Global Role
 │
 └── BotAccess
       └── Bot Role
```

Глобальная роль определяет системные полномочия.

Роль внутри Bot определяет доступные действия в контексте конкретного Bot.

---

# Примеры ролей

В системе могут существовать стандартные роли:

```text
Owner
Administrator
Operator
Support
Analyst
Content Manager
```

Конкретный набор ролей не должен быть жёстко связан с UI.

---

# Состав роли

Каждая роль содержит набор permissions.

Например:

```text
Content Manager
├── bot.view
├── flow.view
├── flow.update
├── flow.sandbox
└── flow.publish
```

или:

```text
Operator
├── bot.view
├── conversation.view
├── member.view
└── statistics.view
```

---

# Принцип наименьших привилегий

Роль должна предоставлять только необходимый набор permissions.

Не следует автоматически объединять все права в одну универсальную роль.

Например, пользователь, работающий с Conversation, не должен автоматически получать:

```text
user.manage
system.settings.manage
bot-access.grant
broadcast.send
```

---

# Системные и Bot-роли

Role должна явно принадлежать определённому контексту применения.

Возможны:

```text
System Role
```

и:

```text
Bot Role
```

Системная роль используется для глобальных административных возможностей.

Bot Role используется в рамках конкретного Bot через BotAccess.

---

# Создание роли

Создание роли является административной операцией и требует соответствующего permission.

При создании необходимо определить:

* название;
* стабильный код;
* область применения;
* набор permissions;
* статус роли.

---

# Публичный code роли

Роль должна иметь стабильный технический `code`.

Например:

```text
owner
administrator
operator
support
analyst
content-manager
```

Code используется внутри системы и не должен зависеть от текста интерфейса.

---

# Изменение роли

Изменение состава permissions роли является критической административной операцией.

После изменения новые проверки используют новый набор permissions.

История прошлых операций User не изменяется.

---

# Назначение роли

Назначение роли User выполняется через Application Use Case.

```text
User
  ↓
Authorization
  ↓
Assign Role
  ↓
Role
```

User не может назначить себе роль, которая расширяет его собственные полномочия сверх разрешённого уровня.

---

# Защита от повышения полномочий

Перед назначением роли необходимо проверить:

* имеет ли Actor право управлять ролями;
* может ли Actor назначать эту роль;
* не создаёт ли операция повышение полномочий за пределами допустимой политики.

UI не является защитой от privilege escalation.

---

# Системные роли

Некоторые роли могут быть системными и не подлежать удалению через обычную админку.

Например:

```text
Owner
Administrator
```

Для таких ролей изменения могут быть ограничены отдельной политикой.

---

# Удаление роли

Роль нельзя физически удалить, если она используется активными User или BotAccess.

Перед удалением необходимо:

* проверить назначения;
* либо заменить роль;
* либо перевести роль в неактивное состояние.

История использования роли должна сохраняться в аудите.

---

# Отключение роли

Роль может быть переведена в неактивное состояние.

Неактивная роль не должна назначаться новым User или BotAccess.

Вопрос уже существующих назначений решается отдельной политикой миграции ролей.

---

# Аудит

Следующие действия должны аудироваться:

```text
role.created
role.updated
role.disabled
role.deleted
role.assigned
role.revoked
role.permissions.updated
```

В аудите должны быть доступны:

```text
Actor User
Target User / BotAccess
Role
Old permissions
New permissions
Date / Time
```

---

# Permissions

Подробные правила permissions описаны в:

`docs/admin/permissions.md`

Role только группирует permissions и не заменяет сам механизм проверки.

---

# MoonShine

MoonShine может использовать Role для:

* списка ролей;
* редактирования состава permissions;
* назначения ролей;
* отображения текущих полномочий.

Однако бизнес-правила RBAC должны выполняться не только в MoonShine.

---

# Инварианты

Всегда должны соблюдаться следующие правила:

* Role группирует permissions;
* Role не определяет BotAccess;
* User не получает доступ к Bot только благодаря наличию роли, если политика не предусматривает это явно;
* назначение роли проверяется сервером;
* критические изменения ролей аудируются;
* системные роли могут иметь ограничения на изменение и удаление;
* неиспользуемые роли можно архивировать или отключать вместо физического удаления.
