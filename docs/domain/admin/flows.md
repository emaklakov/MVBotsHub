# Flows

**Документ:** `docs/admin/flows.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

Настоящий документ описывает административное управление `Flow` внутри выбранного `Bot`.

Бизнес-модель Flow и Workflow Engine описаны в:

`docs/domain/flow/README.md`

Настоящий документ определяет только административные сценарии: список, создание, редактирование, Sandbox, публикацию, управление статусом, версиями и правами доступа.

---

# Контекст Bot

Все операции с Flow выполняются в контексте конкретного Bot.

```text
MVBotsHub
    ↓
Bot
    ↓
Flows
```

Перед выполнением любой операции система должна проверить:

```text
User authenticated
        ↓
Global Permission
        ↓
BotAccess
        ↓
Flow Permission
        ↓
Flow belongs to Bot
```

Прямой доступ к Flow по URL или внутреннему `id` не должен обходить проверку доступа к Bot.

---

# Список Flow

В списке отображаются только Flow выбранного Bot, доступные текущему User.

Каждая запись может отображать:

* название;
* `code`;
* статус;
* активную опубликованную версию;
* наличие неопубликованных изменений;
* количество Trigger;
* порядок отображения `sort`;
* дату последнего изменения.

Порядок списка определяется полем `sort`.

---

# Фильтрация

Список Flow должен поддерживать как минимум фильтрацию по:

```text
status
code
name
```

Поиск и фильтрация должны выполняться в серверном запросе, а не после загрузки всех Flow в память приложения.

---

# Создание Flow

Создание выполняется через Application Use Case.

```text
MoonShine / Flow Editor
        ↓
CreateFlow
        ↓
Flow
        ↓
FlowDraft
```

При создании:

* генерируется уникальный `code`, либо пользователь задаёт его вручную, если это разрешено;
* создаётся FlowDraft;
* опубликованных версий ещё нет;
* Flow не становится доступным пользователям до первой публикации и перехода в допустимое рабочее состояние.

---

# Редактирование

Редактирование сценария выполняется только через `FlowDraft`.

```text
Flow
  ↓
FlowDraft
  ↓
Vue Flow Editor
```

Опубликованная `FlowVersion` никогда не редактируется.

---

# Автосохранение

Изменения Draft сохраняются автоматически.

Административный интерфейс может показывать состояние:

```text
Сохранено
Сохранение...
Ошибка сохранения
```

Автосохранение изменяет только Draft и не создаёт новую опубликованную версию.

---

# Sandbox

Пользователь с соответствующим permission может запускать текущий Draft в Sandbox.

```text
FlowDraft
   ↓
FlowCompiler
   ↓
Sandbox
```

Sandbox не влияет на пользователей Production и не изменяет активную FlowVersion.

---

# Валидация

Перед публикацией Flow проходит `FlowCompiler`.

Административный интерфейс должен отображать результаты проверки:

```text
Ошибки
Предупреждения
```

Наличие критических ошибок блокирует публикацию.

---

# Публикация

Для публикации требуется permission:

```text
flow.publish
```

Общий сценарий:

```text
Draft
   ↓
FlowCompiler
   ↓
Validation
   ↓
PublishFlow
   ↓
FlowVersion
```

Публикация является атомарной операцией.

После успешной публикации:

* создаётся новая FlowVersion;
* обновляется активная версия Flow;
* Draft фиксирует новую базовую опубликованную версию;
* предыдущие версии сохраняются.

---

# Наличие неопубликованных изменений

Административный интерфейс должен явно показывать состояние:

```text
Нет изменений
```

или:

```text
Есть неопубликованные изменения
```

Наличие изменений определяется относительно `FlowDraft.published_version_id`.

---

# Версии

В интерфейсе Flow должен быть доступен просмотр истории опубликованных версий.

Например:

```text
registration@1
registration@2
registration@3
registration@4
```

Для каждой версии могут отображаться:

* номер версии;
* время публикации;
* User, выполнивший публикацию;
* checksum;
* статус использования;
* дополнительная диагностическая информация.

Опубликованная версия является неизменяемой.

---

# Активная версия

В интерфейсе должна быть явно обозначена активная версия Flow.

Например:

```text
registration@4

Активная версия
```

Новые пользовательские FlowSession запускаются относительно активной версии.

Уже выполняющиеся FlowSession не переключаются автоматически на новую версию.

---

# Изменение активной версии

Изменение активной версии является контролируемой административной операцией.

Если система поддерживает возврат к предыдущей версии, он должен выполняться через согласованный процесс публикации новой версии, а не через изменение уже существующей FlowVersion.

История публикаций не переписывается.

---

# Архивация

User с соответствующим permission может перевести Flow в `Archived`.

Перед архивацией система должна проверить ограничения бизнес-модели, включая активные выполнения и зависимости от других Flow.

Архивированный Flow:

* не запускается новым пользователям;
* сохраняет Draft;
* сохраняет опубликованные версии;
* сохраняет Trigger;
* может быть восстановлен.

---

# Отключение

Flow может быть временно переведён в `Disabled`.

При этом:

* новые запуски запрещаются;
* существующие FlowSession не должны автоматически уничтожаться;
* история и версии сохраняются.

---

# Удаление

Административная операция `Delete` означает Soft Delete.

После удаления:

* Flow скрывается из обычных списков;
* новые запуски запрещаются;
* версии сохраняются;
* Draft сохраняется;
* история выполнения не удаляется.

Физическое удаление не выполняется в обычном административном процессе.

---

# Восстановление

User с соответствующим permission может восстановить Flow, если бизнес-правила позволяют это.

После восстановления сохраняются:

* Draft;
* FlowVersion;
* Trigger;
* `code`;
* история публикаций.

Восстановление не должно изменять исторические версии.

---

# FlowTrigger

Административная панель предоставляет управление Trigger выбранного Flow.

Например:

```text
/start
/help
Deep Link
Callback
Keyword
```

Для Trigger доступны операции в пределах permissions:

```text
flow-trigger.view
flow-trigger.create
flow-trigger.update
flow-trigger.delete
```

Подробная бизнес-модель:

`docs/domain/flow/flow-trigger.md`

---

# FlowCall и зависимости

При изменении или удалении Flow система должна учитывать ссылки `FlowCall` из опубликованных сценариев.

Например:

```text
Flow A
   ↓
FlowCall
   ↓
Flow B
```

Нельзя выполнить административную операцию, которая приводит к нарушению опубликованного графа, без предусмотренного бизнес-механизма.

---

# Права доступа

Основные permissions:

```text
flow.view
flow.create
flow.update
flow.publish
flow.disable
flow.archive
flow.restore
flow.delete
flow.version.view
flow.sandbox
```

Конкретный набор может расширяться.

`flow.update` не должен автоматически давать право `flow.publish`.

---

# Аудит

Критические действия Flow должны фиксироваться в административном аудите.

Например:

```text
Flow created
Draft updated
Sandbox started
Flow published
Flow disabled
Flow archived
Flow restored
Flow deleted
Trigger changed
```

Аудит должен содержать как минимум:

```text
User
Bot
Flow
Operation
Date / Time
Result
```

---

# Уведомления

Некоторые операции могут формировать административное уведомление User.

Например:

* публикация завершена;
* публикация отклонена Compiler;
* Sandbox завершён ошибкой;
* фоновая операция завершена.

Notification не является заменой аудита.

---

# Безопасность

MoonShine может скрывать недоступные действия, но это не является механизмом безопасности.

Каждая операция должна повторно проходить серверную проверку:

```text
User
  ↓
Permission
  ↓
BotAccess
  ↓
Flow relation
  ↓
Operation
```

---

# Инварианты

Всегда должны соблюдаться следующие правила:

* User работает только с Flow доступного ему Bot;
* Draft является единственным редактируемым состоянием сценария;
* Published FlowVersion не редактируется;
* публикация требует отдельного permission;
* Sandbox не влияет на Production;
* исторические версии не изменяются;
* удаление является Soft Delete;
* дочерний Flow не может быть изменён так, чтобы сломать опубликованные ссылки без предусмотренного механизма;
* UI не является единственным уровнем авторизации.
