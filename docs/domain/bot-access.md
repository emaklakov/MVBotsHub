# BotAccess

**Документ:** `docs/domain/bot-access.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

`BotAccess` определяет право конкретного `User` работать с конкретным `Bot`.

BotAccess является связующим объектом между административной подсистемой и агрегатом `Bot`.

Он не определяет глобальные права пользователя в системе, а отвечает только за доступ к конкретному Bot.

---

# Ответственность

BotAccess отвечает за:

* связь `User` с `Bot`;
* роль пользователя в рамках конкретного Bot;
* возможность определить доступ пользователя к Bot;
* срок действия доступа, если он используется;
* фиксацию пользователя, выдавшего доступ.

BotAccess не отвечает за:

* глобальную авторизацию `User`;
* глобальные роли и permissions системы;
* настройки Bot;
* пользователей Bot;
* права `Person` или `BotMember`;
* выполнение Flow;
* отправку сообщений.

---

# User и BotAccess

`User` — пользователь MVBotsHub, работающий с административной частью системы.

Один User может иметь доступ к нескольким Bot.

```text
User
 │
 ├── BotAccess → Bot A
 ├── BotAccess → Bot B
 └── BotAccess → Bot C
```

Один Bot также может быть доступен нескольким User.

```text
Bot
 │
 ├── BotAccess ← User A
 ├── BotAccess ← User B
 └── BotAccess ← User C
```

---

# Уровни доступа

Права пользователя определяются на двух уровнях.

## Глобальный уровень

Определяет, что `User` вообще может делать в MVBotsHub.

Например:

* создавать Bot;
* управлять пользователями;
* просматривать системные настройки.

Глобальные роли и permissions относятся к административной подсистеме.

---

## Уровень конкретного Bot

BotAccess определяет, что пользователь может делать внутри конкретного Bot.

Например:

* редактировать Flow;
* создавать Broadcast;
* просматривать Conversation;
* просматривать статистику;
* управлять настройками Bot.

Глобальное наличие permission не означает автоматически наличие доступа к конкретному Bot.

---

# Роль в Bot

BotAccess содержит роль пользователя в рамках конкретного Bot.

В качестве ролей могут использоваться существующие механизмы RBAC приложения.

Примеры ролей:

```text
Owner
Administrator
Operator
Support
Analyst
Content Manager
```

Конкретный набор ролей определяется административной подсистемой и не является фиксированной частью Domain Bot.

---

# Права

Роль определяет набор permissions, разрешённых пользователю внутри Bot.

Примеры permissions:

```text
bot.view
bot.update
flow.view
flow.update
flow.publish
broadcast.view
broadcast.create
broadcast.send
conversation.view
member.view
statistics.view
```

Проверка выполняется как комбинация:

```text
Global Permission
        +
BotAccess
        +
Bot-level Permission
```

---

# Владение Bot

`Bot` не содержит отдельного `owner_id` в качестве механизма авторизации.

Владелец определяется через BotAccess и соответствующую роль.

Например:

```text
Bot A
   │
   └── BotAccess
          ├── User A → Owner
          ├── User B → Operator
          └── User C → Analyst
```

Это позволяет менять владельца или набор ответственных пользователей без изменения самого `Bot`.

---

# Публичный доступ к Bot

По умолчанию `User` видит в административной панели только те Bot, для которых существует действующий BotAccess или глобальное системное право, позволяющее обходить это ограничение.

Обычный пользователь без BotAccess не должен видеть Bot в рабочих списках.

Это правило должно применяться не только к списку Bot, но и к доступу к связанным ресурсам.

---

# Создание Bot

При создании нового Bot должен автоматически создаваться BotAccess для User, создавшего Bot.

Создаваемый доступ получает роль, определённую политикой приложения как роль владельца.

Таким образом после создания User сразу имеет доступ к своему Bot.

---

# Выдача доступа

Пользователь с соответствующим permission может выдать другому User доступ к Bot.

Общий процесс:

```text
User A
  │
  ▼
Bot
  │
  ▼
Создать BotAccess
  │
  ▼
User B получает доступ
```

Выдаваемая роль должна быть разрешена правами User A.

Пользователь не должен иметь возможность выдать права выше собственных полномочий, если это запрещено политикой RBAC.

---

# Изменение роли

Роль существующего BotAccess может быть изменена пользователем с соответствующим permission.

Изменение роли:

* не изменяет Bot;
* не изменяет других пользователей;
* немедленно влияет на последующие проверки доступа.

История изменений прав должна фиксироваться административным аудитом.

---

# Отзыв доступа

BotAccess может быть отозван.

После отзыва:

* User перестаёт видеть Bot в обычных списках;
* новые операции над Bot запрещаются;
* доступ к связанным ресурсам запрещается;
* исторические действия User не изменяются.

Уже выполняющиеся операции должны завершаться по правилам Application и Infrastructure.

---

# Временный доступ

BotAccess может иметь срок действия.

Например:

```text
expires_at = 2026-08-31 23:59:59
```

После истечения срока доступ считается недействующим.

Если срок не задан, доступ считается постоянным до его отзыва.

---

# Создатель доступа

Для аудита рекомендуется хранить `created_by` — User, выдавшего доступ.

Это позволяет определить:

```text
Кто
→
кому
→
к какому Bot
→
какую роль
→
когда
```

выдал.

---

# Уникальность

Для одной пары:

```text
User + Bot
```

должен существовать один действующий BotAccess.

Несколько одновременно действующих записей доступа для одной пары не допускаются.

Если потребуется изменить роль, изменяется существующий доступ либо старый доступ закрывается и создаётся новый в рамках отдельного правила аудита.

---

# Доступ к ресурсам Bot

Проверка BotAccess должна распространяться на все ресурсы, принадлежащие Bot.

Например:

```text
Bot
├── Flow
├── FlowDraft
├── FlowVersion
├── Broadcast
├── Conversation
├── BotMember
├── BotSettings
└── Localization
```

Наличие прямого URL или внутреннего идентификатора ресурса не должно позволять обойти проверку доступа к родительскому Bot.

---

# BotAccess и Domain

BotAccess описывает бизнес-отношение:

```text
User ↔ Bot
```

При этом конкретная реализация ролей и permissions относится к административной подсистеме.

Domain Bot не должен зависеть от MoonShine.

---

# BotAccess и MoonShine

MoonShine является Presentation Layer.

MoonShine может использовать BotAccess для:

* фильтрации списка Bot;
* ограничения доступа к Resources;
* управления выдачей прав;
* отображения роли User внутри Bot.

Однако правила доступа не должны быть реализованы только внутри MoonShine.

Application должен предоставлять централизованную проверку доступа.

---

# BotAccess и `App\Models\User\User`

Текущая реализация пользователя системы находится в административной подсистеме приложения.

Конкретное расположение модели:

```text
App\Models\User\User
```

Документ Domain использует термин `User` и не зависит от физического пространства имён реализации.

---

# Soft Delete

BotAccess не должен физически удаляться при обычном отзыве доступа, если это требуется для аудита.

Предпочтительно использовать состояние доступа или Soft Delete, позволяющее сохранить историю выдачи и отзыва прав.

При повторной выдаче доступа новая активная запись может быть создана в соответствии с принятой политикой аудита.

---

# Инварианты

Всегда должны соблюдаться следующие правила:

* BotAccess связывает одного User и одного Bot;
* без действующего BotAccess пользователь не имеет обычного доступа к Bot;
* один User может иметь доступ к множеству Bot;
* один Bot может быть доступен множеству User;
* Bot не хранит отдельный `owner_id` как механизм авторизации;
* глобальные permissions и BotAccess проверяются независимо;
* User не может выдать права выше собственных полномочий, если это запрещено RBAC-политикой;
* отзыв доступа не изменяет историю действий User;
* доступ к дочерним ресурсам не может обходить доступ к Bot;
* внутренние `id` не используются как единственный механизм авторизации.

---

# Аудит

Операции с BotAccess должны быть доступны для административного аудита.

Минимально должны фиксироваться:

* выдача доступа;
* изменение роли;
* отзыв доступа;
* изменение срока действия;
* восстановление доступа.

Аудит является частью административной подсистемы и не должен быть встроен в сам Bot.

---

# Производительность

Проверка BotAccess выполняется часто, поэтому механизм доступа должен быть пригоден для кэширования.

Кэш не является источником истины.

Изменение доступа должно корректно инвалидировать связанные кэши.

---

# Будущие возможности

Архитектура допускает:

* несколько ролей при необходимости будущего расширения RBAC;
* временные доступы;
* доступ по группам User;
* массовую выдачу доступа;
* аудит изменений;
* делегирование управления Bot;
* дополнительные ограничения на отдельные разделы Bot.
