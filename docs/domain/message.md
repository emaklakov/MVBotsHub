# Message

**Документ:** `docs/domain/message.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

`Message` представляет одно зафиксированное сообщение в рамках `Conversation`.

Message является составной частью агрегата `Conversation` и не имеет самостоятельного жизненного цикла вне этого агрегата.

Сообщение является историческим фактом взаимодействия и после фиксации не изменяется.

---

# Ответственность

Message отвечает за:

* фиксацию содержимого сообщения;
* фиксацию направления сообщения;
* фиксацию источника и типа события;
* хранение времени создания;
* хранение результата доставки для исходящего сообщения, если это относится к истории сообщения;
* связь сообщения с Conversation.

Message не отвечает за:

* выполнение Flow;
* хранение текущего состояния FlowSession;
* маршрутизацию событий;
* отправку сообщения в Telegram;
* очереди;
* управление Conversation;
* хранение персональных данных Person.

---

# Принадлежность

Каждый Message принадлежит одному `Conversation`.

```text
Conversation
    │
    ├── Message
    ├── Message
    ├── Message
    └── ...
```

Message не может существовать как независимая бизнес-сущность без Conversation.

---

# Направление сообщения

На концептуальном уровне Message имеет направление.

```text
Incoming
Outgoing
```

## Incoming

Сообщение поступило от пользователя или другого внешнего источника события.

## Outgoing

Сообщение было сформировано системой, Flow или оператором и предназначено для доставки участнику Conversation.

---

# Тип сообщения

Message дополнительно содержит тип содержимого.

Примеры:

```text
text
image
document
video
audio
location
contact
sticker
callback
system
```

Конкретный набор типов может расширяться.

Тип сообщения не должен быть привязан только к Telegram API.

---

# Основные свойства

| Свойство        | Назначение                                                     |
| --------------- | -------------------------------------------------------------- |
| id              | Внутренний идентификатор                                       |
| conversation_id | Родительский Conversation                                      |
| direction       | Направление сообщения                                          |
| type            | Тип содержимого                                                |
| content         | Содержимое                                                     |
| external_id     | Идентификатор сообщения во внешнем транспорте, если существует |
| sender_type     | Источник сообщения                                             |
| sent_at         | Время отправки/получения                                       |
| created_at      | Время фиксации сообщения                                       |

Конкретный состав полей может расширяться для поддержки новых каналов и типов сообщений.

---

# Содержимое

Message хранит содержимое, необходимое для восстановления факта общения.

Например для текстового сообщения:

```json
{
    "text": "Здравствуйте!"
}
```

Для мультимедиа может использоваться ссылка на `Media` или внешний ресурс, а не бинарное содержимое непосредственно в Message.

---

# Внешний идентификатор

`external_id` хранит идентификатор сообщения во внешнем транспортном канале, если такой идентификатор существует.

Например, для Telegram это может быть идентификатор сообщения Telegram.

Этот идентификатор используется для:

* корреляции;
* диагностики;
* идемпотентности;
* связи внутреннего сообщения с внешним событием.

Внешний идентификатор не является идентификатором самого Message в Domain.

---

# Источник сообщения

Message должен позволять определить источник сообщения.

Например:

```text
Person
Bot
Operator
System
External
```

Это логическое понятие и не должно зависеть от конкретного транспорта.

Например, Telegram является транспортом, а не значением `sender_type`.

---

# Incoming Message

Входящее сообщение фиксирует факт получения содержимого от внешнего источника.

Общий поток:

```text
External Event
      ↓
Transport Adapter
      ↓
Normalize Event
      ↓
Conversation
      ↓
Message(Incoming)
```

После фиксации Message может участвовать в продолжении FlowSession или в маршрутизации нового Flow.

---

# Outgoing Message

Исходящее Message фиксирует факт сообщения, которое система должна отправить или отправила участнику Conversation.

Общий поток:

```text
Flow / Application
      ↓
Send Message Command
      ↓
Transport Gateway
      ↓
Message(Outgoing)
```

Фактическая доставка выполняется Infrastructure.

---

# Фиксация сообщения и доставка

Необходимо различать:

```text
Message создан
```

и:

```text
Message доставлен
```

Создание Message не является доказательством успешной доставки внешним транспортом.

Если транспорт предоставляет отдельный результат доставки, он должен быть связан с Message через отдельное состояние или событие доставки.

---

# Историческая неизменяемость

После фиксации Message не изменяется.

Не допускается задним числом изменять:

* содержимое;
* направление;
* время;
* источник;
* внешний идентификатор;
* исторический результат операции.

Если требуется новое состояние, создаётся новая запись или новое событие, а история остаётся неизменной.

---

# Immutable History

Message является частью принципа `Immutable History` платформы.

История сообщений используется для:

* анализа диалогов;
* аналитики;
* аудита;
* расследования ошибок;
* CRM-функций;
* будущих AI-сценариев.

Историческое сообщение не должно переписываться после фиксации.

---

# Связь с Conversation

Conversation управляет жизненным циклом Message.

Conversation определяет:

* к какому сеансу общения относится Message;
* порядок сообщений;
* активность Conversation;
* завершение Conversation.

Message не определяет, должен ли Conversation оставаться активным.

---

# Связь с FlowSession

Message и `FlowSession` не являются частью одного жизненного цикла.

Message может инициировать или продолжать FlowSession, но не принадлежит ей.

```text
Message
   │
   │ событие
   ▼
FlowSession
```

Таким образом Message не является дочерней сущностью FlowSession.

Это решение предотвращает искусственную связанность истории сообщений с выполнением сценария.

---

# Связь с Flow

Message не содержит ссылку на FlowVersion как обязательную часть своей модели.

При необходимости происхождение сообщения от конкретного Flow или Node может фиксироваться дополнительными метаданными или отдельным событием аудита.

История сообщения должна оставаться валидной даже после завершения или архивирования соответствующей FlowSession.

---

# Локализация

Message хранит фактически зафиксированное содержимое сообщения.

Изменение переводов в `Localization` не должно изменять уже созданный Message.

Например:

```text
FlowVersion
    ↓
сформирован текст на kk
    ↓
Message
    ↓
"Сәлем!"
```

Позднейшее изменение перевода не изменяет историческое сообщение.

---

# Media

Для бинарных данных Message может содержать ссылку на Media.

Например:

```text
Message
   ↓
Media
   ↓
File Storage
```

Бинарный файл не должен храниться непосредственно внутри Message.

---

# Идемпотентность

При обработке внешних событий система должна предотвращать создание дубликатов одного и того же входящего Message.

Для этого могут использоваться:

* внешний идентификатор;
* идентификатор события;
* комбинация транспортных атрибутов;
* другие механизмы корреляции.

Конкретная реализация относится к Application/Infrastructure.

---

# Удаление

Message не удаляется физически в рамках обычного жизненного цикла Conversation.

История должна сохраняться.

Если требуется удаление персональных данных, применяется политика анонимизации или иная согласованная политика обработки данных без нарушения целостности исторических событий там, где сохранение истории допускается требованиями проекта.

---

# Безопасность

Message может содержать персональные и чувствительные данные.

Поэтому:

* содержимое не должно без необходимости попадать в системные логи;
* доступ к сообщениям должен контролироваться правами на соответствующий Bot;
* экспорт сообщений должен учитывать права User;
* секреты не должны сохраняться как обычное содержимое сообщения без специального бизнес-смысла.

---

# Производительность

Conversation может содержать большое количество Message.

Архитектура должна позволять:

* быстро получать последние сообщения;
* постранично читать историю;
* не загружать весь Conversation целиком;
* хранить большие объёмы исторических сообщений;
* индексировать внешние идентификаторы и время.

Конкретная оптимизация хранения относится к Infrastructure/Database.

---

# Инварианты

Всегда должны соблюдаться следующие правила:

* Message принадлежит одному Conversation;
* Message не является отдельным Aggregate Root;
* историческое Message не изменяется;
* историческое Message не удаляется в обычном жизненном цикле;
* Message не хранит состояние FlowSession;
* Message не выполняет Flow;
* Message не взаимодействует с Telegram API;
* историческое содержимое не изменяется из-за новых переводов;
* повторная доставка одного внешнего события не должна создавать дубликат Message.

---

# Будущие возможности

Архитектура допускает:

* реакции;
* редактирование внешнего сообщения с фиксацией отдельного события;
* цитирование;
* ответы на сообщения;
* вложения;
* сообщения операторов;
* сообщения AI;
* сообщения нескольких каналов;
* threading;
* сообщения с интерактивными элементами.
