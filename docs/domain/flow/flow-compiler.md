# FlowCompiler

**Документ:** `docs/domain/flow/flow-compiler.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

`FlowCompiler` отвечает за проверку и подготовку `FlowDraft` к публикации.

Compiler преобразует редактируемый Draft в неизменяемый опубликованный `FlowVersion`.

Общая последовательность:

```text
FlowDraft
    │
    ▼
FlowCompiler
    │
    ├── Validation
    ├── Reference Resolution
    ├── Normalization
    └── Compilation
    │
    ▼
Compiled Flow
    │
    ▼
FlowVersion
```

FlowCompiler является обязательным этапом перед публикацией любого Flow.

---

# Основной принцип

`FlowDraft` может находиться в незавершённом или невалидном состоянии.

`FlowVersion` — никогда.

Следовательно:

```text
Draft
    ↓
может быть невалидным

FlowCompiler
    ↓
проверяет

FlowVersion
    ↓
должна быть исполнимой
```

---

# Ответственность

FlowCompiler отвечает за:

- структурную проверку Flow JSON;
- проверку Node;
- проверку Edge;
- проверку ссылок;
- проверку FlowCall;
- проверку публичных `code`;
- проверку обязательных settings;
- проверку совместимости `schema_version`;
- нормализацию JSON;
- подготовку неизменяемого графа для публикации;
- формирование результата компиляции;
- отказ от публикации при критических ошибках.

FlowCompiler не отвечает за:

- редактирование Draft;
- сохранение Draft;
- выполнение Flow;
- выполнение Node;
- создание FlowSession;
- маршрутизацию событий;
- отправку сообщений;
- взаимодействие с Telegram;
- непосредственное управление пользовательским интерфейсом.

---

# Место в архитектуре

```text
Vue Editor

↓

FlowDraft

↓

FlowCompiler

↓

Validation / Compilation

↓

FlowVersion

↓

FlowEngine
```

Compiler находится между редактором и runtime.

---

# Входные данные

FlowCompiler получает:

- `Flow`;
- `FlowDraft`;
- поддерживаемую `schema_version`;
- доступные Flow данного Bot;
- доступные типы Node;
- необходимые настройки компиляции.

Compiler не должен самостоятельно загружать произвольные данные из Infrastructure.

Все необходимые зависимости предоставляются Application Layer.

---

# Результат компиляции

Результатом работы Compiler является структурированный `CompilationResult`.

Концептуально:

```text
CompilationResult

├── success
├── graph
├── warnings
├── errors
└── metadata
```

При наличии критических ошибок:

```text
success = false
```

и FlowVersion не создаётся.

---

# Ошибки и предупреждения

Compiler должен различать:

## Error

Критическая проблема.

Публикация запрещена.

Примеры:

- неизвестный Node type;
- дублирующийся Node.id;
- отсутствующий target Edge;
- несуществующий Flow;
- отсутствующий обязательный параметр.

---

## Warning

Некритическая проблема.

Публикация может быть разрешена в зависимости от политики бота или проекта.

Примеры:

- недостижимый Node;
- отсутствующий перевод;
- отсутствующий необязательный текст;
- потенциально бесконечный цикл.

---

# Структурная валидация

Compiler должен проверить:

- наличие `schema_version`;
- корректность корневой структуры JSON;
- наличие `nodes`;
- корректность `edges`;
- корректность `variables`;
- наличие `start_node`;
- допустимость типов данных.

---

# Проверка Node

Для каждого Node проверяется:

- наличие `id`;
- уникальность `id`;
- наличие `type`;
- наличие необходимого `settings`;
- поддерживаемость `type`;
- соответствие settings схеме Node.

Например:

```text
Node.type = message

↓

MessageNode schema

↓

проверка settings
```

---

# Проверка Edge

Для каждого Edge проверяется:

- наличие `id`;
- уникальность `id`;
- наличие `source`;
- наличие `target`;
- существование source Node;
- существование target Node.

Например:

```text
Edge.source = node-a

Edge.target = node-b
```

оба Node должны существовать.

---

# Проверка Start Node

`start_node` должен:

- существовать;
- ссылаться на существующий Node;
- быть допустимым для запуска Flow.

Flow без корректной точки входа не может быть опубликован.

---

# Проверка конечных узлов

Compiler должен убедиться, что структура сценария содержит корректный способ завершения выполнения.

Например:

```text
flow.end
```

или другой явно определённый механизм завершения.

Сам факт отсутствия исходящих Edge не должен автоматически считаться корректным завершением.

---

# Проверка достижимости

Compiler может определить:

- недостижимые Node;
- полностью изолированные участки графа;
- Node, которые никогда не могут быть достигнуты из `start_node`.

Такие случаи не всегда являются ошибкой.

По умолчанию они должны формировать `Warning`, если бизнес-правила Flow не требуют иного.

---

# Проверка циклов

Циклы разрешены.

Например:

```text
A
↓
B
↓
C
↓
A
```

Это может быть корректным сценарием.

Compiler не должен запрещать циклы как таковые.

Он должен только выявлять потенциально опасные структуры и, при необходимости, выдавать предупреждение.

Ограничение реального выполнения циклов выполняется `FlowEngine`.

---

# Проверка FlowCall

Для каждого:

```text
flow.call
```

Compiler должен проверить:

- наличие `settings.flow`;
- существование Flow по публичному `code`;
- принадлежность целевого Flow тому же Bot;
- доступность целевого Flow;
- корректность параметров вызова;
- возможность разрешить зависимость.

Например:

```json
{
    "type": "flow.call",
    "settings": {
        "flow": "checkout",
        "return": true
    }
}
```

Flow `checkout` должен существовать в пределах текущего Bot.

---

# Циклические зависимости Flow

Следует различать:

## Цикл внутри одного Flow

```text
A → B → C → A
```

Допустим.

---

## Циклический вызов Flow

```text
Flow A
    ↓
Flow B
    ↓
Flow A
```

Такой вызов также может быть допустимым, поскольку FlowStack имеет ограничение глубины и FlowEngine контролирует выполнение.

Однако Compiler должен выявлять потенциальные циклические зависимости Flow и выдавать предупреждение, если они могут привести к бесконечной рекурсии.

---

# Проверка NodeHandler

Для каждого `Node.type` Compiler должен убедиться, что существует зарегистрированный NodeHandler.

Например:

```text
message
    ↓
NodeHandlerRegistry
    ↓
MessageNodeHandler
```

Если Handler отсутствует:

```text
ERROR
Node handler not found
```

Публикация запрещается.

---

# Проверка схемы Node

Каждый Node type должен иметь определённую схему конфигурации.

Например:

```text
message
```

может требовать:

```json
{
    "text": "..."
}
```

а:

```text
input.text
```

может требовать:

```json
{
    "variable": "customer_name"
}
```

Compiler выполняет эту проверку до публикации.

---

# Проверка переменных

Compiler должен проверять ссылки на переменные:

- существование;
- корректность `code`;
- совместимость типов;
- допустимость области видимости.

Например:

```text
customer_name
```

не должен ссылаться на неизвестную переменную без специальной декларации.

При этом система должна различать:

```text
Session Variables
```

и:

```text
Member Variables
```

---

# Проверка локализации

Compiler должен уметь определить состояние локализации Flow.

Например:

```text
Русский
English
Қазақша
```

И определить:

```text
100 %
80 %
45 %
```

При этом отсутствие перевода не является универсальной ошибкой.

Политика определяется настройками Bot.

Например:

```text
strict localization = true
```

может запрещать публикацию при отсутствии обязательных переводов.

---

# Проверка ссылок на Media

Если Node содержит ссылку на Media через публичный `code`, Compiler должен убедиться, что соответствующий Media существует и доступен.

Например:

```json
{
    "media": "welcome-image"
}
```

Если Media не существует:

```text
ERROR
```

---

# Проверка внешних ссылок

Если Node содержит ссылку на:

- Credential;
- Integration;
- external resource;

Compiler должен проверить существование ссылки и допустимость её использования.

Секреты при этом не должны попадать в опубликованный JSON.

---

# Нормализация

Перед публикацией Compiler может привести JSON к каноническому виду.

Например:

- нормализовать порядок секций;
- удалить неиспользуемые временные данные редактора;
- нормализовать пустые значения;
- привести структуру к поддерживаемой `schema_version`;
- стабилизировать представление JSON.

Это необходимо для:

- стабильного `checksum`;
- предсказуемого Diff;
- воспроизводимой публикации.

---

# Разделение Editor и Runtime

Draft может содержать редакторские данные:

```text
position
viewport
minimap
collapsed
```

Compiler должен определить, какие данные:

```text
Editor-only
```

а какие:

```text
Runtime
```

Editor-only данные могут не попадать в опубликованную Runtime-структуру.

Таким образом:

```text
Draft JSON
    ↓
Compiler
    ↓
Published Runtime JSON
```

---

# Компиляция Flow JSON

После успешной валидации Compiler создаёт подготовленную структуру для `FlowVersion`.

Процесс:

```text
Draft JSON

↓

Parse

↓

Validate

↓

Resolve References

↓

Normalize

↓

Compile

↓

Compiled Graph
```

---

# Compiled Graph

Compiled Graph должен содержать только данные, необходимые для выполнения Flow.

Он может отличаться от визуального Draft JSON.

Например:

```text
Draft

├── editor position
├── viewport
├── UI metadata
└── runtime settings
```

после компиляции:

```text
Compiled Graph

├── nodes
├── edges
├── execution metadata
└── resolved runtime configuration
```

---

# Публикация

Сам Compiler не должен самостоятельно выполнять бизнес-операцию публикации.

Compiler предоставляет результат:

```text
CompilationResult
```

а Application Use Case выполняет атомарную публикацию.

Общая схема:

```text
FlowDraft

↓

FlowCompiler

↓

CompilationResult

↓

PublishFlow

↓

Create FlowVersion
↓

Update Flow.active_version_id
↓

Update FlowDraft.published_version_id
↓

Commit
```

---

# Атомарность

Публикация новой FlowVersion должна выполняться атомарно.

В рамках одной транзакции:

1. результат Compiler считается успешным;
2. создаётся FlowVersion;
3. обновляется `Flow.active_version_id`;
4. обновляется `FlowDraft.published_version_id`;
5. фиксируется публикация.

Если любой шаг не завершён, новая версия не считается опубликованной.

---

# Повторная компиляция

Один и тот же Draft при одинаковых условиях должен давать одинаковый результат компиляции.

Это важно для:

- тестирования;
- диагностики;
- воспроизводимости;
- checksum;
- CI/CD.

Внешние недетерминированные данные не должны менять результат без явной зависимости.

---

# Компиляция и Preview

Compiler может использоваться не только перед публикацией.

Например:

```text
Vue Editor

↓

Validate Draft

↓

FlowCompiler

↓

CompilationResult
```

Пользователь может получать ошибки и предупреждения ещё до публикации.

---

# Sandbox

Для Sandbox допустимо использовать Draft после успешной компиляции без создания `FlowVersion`.

```text
FlowDraft

↓

FlowCompiler

↓

Compiled Draft

↓

Sandbox FlowSession
```

Таким образом Sandbox использует ту же проверку, что и Production, но не создаёт опубликованную версию.

---

# Производительность

Compiler может быть ресурсоёмким для больших Flow.

Поэтому архитектура должна позволять:

- кэшировать результаты;
- повторно использовать промежуточные вычисления;
- выполнять компиляцию асинхронно;
- выполнять публикацию через очередь, если сценарий большой;
- использовать хэши для определения неизменившегося Draft.

Однако сама бизнес-операция публикации должна завершаться только после успешного получения результата компиляции.

---

# Ошибки

Compiler должен возвращать структурированные ошибки.

Например:

```text
errors:
    - node = "send-welcome"
      code = "missing_setting"
      message = "Required setting 'text' is missing"

    - node = "checkout"
      code = "flow_not_found"
      message = "Flow 'checkout' does not exist"
```

Ошибки должны быть пригодны для отображения в редакторе.

---

# Классы ошибок

Рекомендуется различать:

```text
SchemaError
NodeError
EdgeError
ReferenceError
VariableError
LocalizationError
IntegrationError
CompilerError
```

Конкретная реализация может отличаться.

---

# Инварианты

Всегда должны соблюдаться следующие правила.

- Невалидный Draft не может быть опубликован.
- Compiler не изменяет Draft.
- Compiler не изменяет FlowVersion.
- Compiler не создаёт FlowSession.
- Compiler не зависит от Telegram.
- Compiler не хранит постоянное состояние.
- Любой опубликованный FlowVersion должен быть результатом успешной компиляции.
- Все ссылки, необходимые для runtime, должны быть проверены до публикации.
- Неразрешимые ошибки блокируют публикацию.
- Warning не должен автоматически считаться Error без соответствующей политики.
