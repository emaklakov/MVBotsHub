# FlowRouter

**Документ:** `docs/domain/flow/flow-router.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

`FlowRouter` отвечает за определение Flow, который должен быть запущен в ответ на входящее событие.

FlowRouter является компонентом маршрутизации подсистемы Flow.

Он получает нормализованное доменное событие и определяет подходящий `FlowTrigger`.

FlowRouter не выполняет сценарий и не отвечает за обработку отдельных узлов Flow.

---

# Ответственность

FlowRouter отвечает за:

- получение входящего события;
- поиск подходящих FlowTrigger;
- проверку доступности Flow;
- применение приоритетов Trigger;
- выбор одного конечного Flow;
- подготовку данных для создания FlowSession;
- обработку отсутствия подходящего Trigger.

FlowRouter не отвечает за:

- преобразование Telegram Update в доменное событие;
- выполнение Flow;
- выполнение Node;
- отправку сообщений;
- сохранение состояния FlowSession;
- публикацию Flow;
- компиляцию Flow.

---

# Место в архитектуре

FlowRouter работает после транспортного и входного слоя, когда внешнее событие уже приведено к нормализованному внутреннему представлению.

```text
External Event
      │
      ▼
Transport Adapter
      │
      ▼
Domain Event
      │
      ▼
FlowRouter
      │
      ▼
FlowTrigger
      │
      ▼
Flow
      │
      ▼
FlowSession
      │
      ▼
FlowEngine
```

FlowRouter не должен зависеть от Telegram или другого конкретного транспорта.

---

# Входные данные

FlowRouter получает нормализованное событие, содержащее:

- Bot;
- BotMember, если он уже определён;
- Conversation, если она существует;
- тип события;
- данные события;
- метаданные события;
- время события;
- идентификатор события.

Конкретная структура входного события определяется общей моделью событий платформы.

---

# Маршрутизация

Общий алгоритм:

```text
Incoming Event

↓

Определить Bot

↓

Найти активные FlowTrigger

↓

Отфильтровать неподходящие Trigger

↓

Проверить доступность Flow

↓

Отсортировать по priority

↓

Выбрать Trigger

↓

Определить Flow

↓

Передать Flow для запуска
```

---

# Поиск Trigger

FlowRouter работает только с активными Trigger.

Trigger с:

```text
enabled = false
```

не участвуют в маршрутизации.

Flow со статусами:

```text
Disabled
Archived
Deleted
```

не может быть выбран для нового запуска.

---

# TriggerRegistry

FlowRouter не содержит логику проверки конкретных типов Trigger.

Для определения обработчика используется `TriggerRegistry`.

```text
FlowTrigger.type

        │

        ▼

TriggerRegistry

        │

        ▼

TriggerHandler
```

Например:

```text
telegram.command
        ↓
TelegramCommandTriggerHandler
```

или:

```text
telegram.deep_link
        ↓
TelegramDeepLinkTriggerHandler
```

---

# TriggerHandler

`TriggerHandler` получает:

- входящее событие;
- конфигурацию FlowTrigger.

Результат проверки:

```text
Match
```

или:

```text
No Match
```

Handler не запускает Flow.

Он только определяет соответствие события Trigger.

---

# Несколько подходящих Trigger

Одно событие может соответствовать нескольким Trigger.

Например:

```text
/start
```

может совпасть с несколькими правилами, если они настроены некорректно или намеренно пересекаются.

FlowRouter должен обрабатывать такие ситуации детерминированно.

---

# Приоритет

Для выбора между несколькими подходящими Trigger используется `priority`.

Меньшее значение имеет больший приоритет.

Например:

| Trigger | Priority |
|----------|---------:|
| telegram.deep_link | 10 |
| telegram.command | 20 |
| telegram.keyword | 30 |

В результате сначала рассматривается Trigger с `priority = 10`.

---

# Правило детерминированности

Если два Trigger имеют одинаковый `priority` и оба подходят под событие, результат маршрутизации должен оставаться детерминированным.

Система не должна зависеть от случайного порядка записей в базе данных.

В качестве второго уровня сортировки используется стабильный порядок, например идентификатор Trigger или иной определённый системный ключ.

---

# Проверка Flow

После определения подходящего Trigger FlowRouter проверяет, доступен ли связанный Flow для запуска.

Flow должен:

- существовать;
- принадлежать текущему Bot;
- иметь статус `Active`;
- иметь активную опубликованную `FlowVersion`.

Если одно из условий не выполнено, Trigger не может привести к запуску Flow.

---

# Активная версия

FlowRouter не выбирает произвольную версию сценария.

Для нового запуска используется только:

```text
Flow.active_version_id
```

Полученная `FlowVersion` становится основой новой `FlowSession`.

---

# Создание FlowSession

FlowRouter не выполняет FlowSession самостоятельно.

После выбора Flow и его активной версии он передаёт результат следующему Application Use Case.

```text
FlowRouter

↓

Selected Flow
+
Selected FlowVersion

↓

StartFlowSession

↓

FlowSession
```

Это сохраняет разделение ответственности между маршрутизацией и выполнением.

---

# Первичный запуск

Если подходящий FlowTrigger найден и активной FlowSession для соответствующего сценария не существует, создаётся новая FlowSession.

Например:

```text
/start

↓

FlowRouter

↓

main-menu

↓

main-menu@7

↓

FlowSession
```

---

# Вход в уже выполняющийся Flow

Если пользователь уже находится внутри активного Flow, входящее событие может не запускать новый Flow.

В первую очередь система должна определить, предназначено ли событие для продолжения текущей FlowSession.

Высокоуровневый порядок:

```text
Incoming Event

↓

Есть ожидающая FlowSession?

        │
    ┌───┴───┐
    │       │
   Да      Нет
    │       │
    ▼       ▼
Resume    FlowRouter
FlowSession
```

Это особенно важно для событий:

- ответа на вопрос;
- выбора кнопки;
- отправки контакта;
- отправки геолокации;
- других событий, которых ожидает текущий Node.

FlowRouter не должен перехватывать событие, которое предназначено для продолжения уже ожидающего выполнения, если активная FlowSession явно ожидает этот тип события.

---

# Внешний запуск и продолжение

Необходимо различать:

## Start

Запуск нового Flow через Trigger.

```text
/start
    ↓
FlowTrigger
    ↓
FlowSession
```

## Resume

Продолжение уже существующего выполнения.

```text
Message
    ↓
Waiting FlowSession
    ↓
FlowEngine
```

Эти операции не должны смешиваться.

---

# FlowCall

Переход из одного Flow в другой через `FlowCall` не проходит через FlowRouter.

```text
Flow A

↓

FlowCall

↓

Flow B
```

FlowRouter используется для внешних и системных точек входа.

Внутренние переходы выполняет `FlowEngine`.

---

# Отсутствие подходящего Trigger

Если событие не соответствует ни одному активному Trigger и не предназначено для продолжения ожидающей FlowSession, FlowRouter возвращает результат:

```text
No Route
```

На основании этого результата Application может выполнить системную обработку.

Например:

- показать сообщение о неизвестной команде;
- запустить системный Flow;
- проигнорировать событие;
- передать событие оператору.

Сам FlowRouter не определяет текст ответа пользователю.

---

# Ошибки маршрутизации

Ошибки должны быть разделены на два типа.

## Ожидаемый результат

Например:

```text
No Route
```

Это не является исключением.

---

## Системная ошибка

Например:

- не найден зарегистрированный TriggerHandler;
- нарушена конфигурация Trigger;
- обнаружена недопустимая ссылка на Flow.

Такие ошибки должны фиксироваться и передаваться в системный механизм обработки ошибок.

---

# Идемпотентность

FlowRouter должен поддерживать повторную обработку одного и того же входящего события без создания дубликатов FlowSession.

Для этого событие должно иметь уникальный идентификатор.

Перед созданием нового запуска необходимо учитывать уже обработанные события.

Конкретная реализация идемпотентности относится к Application и Infrastructure.

---

# Масштабирование

FlowRouter должен позволять:

- обрабатывать большое количество событий параллельно;
- маршрутизировать события для разных Bot независимо;
- добавлять новые типы Trigger без изменения существующей логики;
- масштабировать обработчики горизонтально.

FlowRouter не должен хранить состояние выполнения в памяти PHP-процесса.

---

# Инварианты

Всегда должны соблюдаться следующие правила.

- FlowRouter не зависит от Telegram.
- FlowRouter не выполняет Flow.
- FlowRouter не выполняет Node.
- FlowRouter не изменяет FlowVersion.
- Отключённые Trigger не участвуют в маршрутизации.
- Неактивные Flow не запускаются.
- Для нового запуска используется только активная FlowVersion.
- Внутренний `FlowCall` не проходит через FlowRouter.
- Выбор Trigger должен быть детерминированным.
- Повторная доставка одного события не должна создавать дублирующее выполнение.

---

# Будущие возможности

Архитектура допускает добавление:

- маршрутизации по сегментам BotMember;
- маршрутизации по языку;
- маршрутизации по тегам;
- маршрутизации по значениям переменных;
- A/B-маршрутизации;
- приоритетных системных Flow;
- fallback Flow;
- маршрутизации по внешним событиям.
