# Flow JSON

**Документ:** `docs/domain/flow/flow-json.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

`Flow JSON` — канонический формат представления графа сценария MVBotsHub.

Формат используется для хранения структуры Flow в:

- `FlowDraft`;
- `FlowVersion`.

Один и тот же формат должен быть пригоден для:

- визуального редактора Vue;
- компиляции;
- выполнения FlowEngine;
- импорта;
- экспорта;
- резервного копирования;
- диагностики;
- сравнения версий.

---

# Основной принцип

Граф сценария хранится как единый JSON-документ.

Структура Flow не разбивается на отдельные таблицы:

```text
flow_nodes
flow_edges
flow_conditions
flow_buttons
...
```

Вместо этого используется единый граф:

```text
Flow JSON
├── metadata
├── nodes
├── edges
└── variables
```

Конкретный набор секций может расширяться в следующих версиях формата.

---

# Версия формата

Каждый Flow JSON должен содержать версию формата.

Например:

```json
{
    "schema_version": 1
}
```

`schema_version` определяет структуру самого JSON-документа.

Не следует путать:

```text
schema_version
```

и:

```text
FlowVersion.version
```

Это разные понятия.

### `schema_version`

Версия формата JSON.

### `FlowVersion.version`

Порядковый номер публикации конкретного Flow.

---

# Общая структура

Минимальная структура:

```json
{
    "schema_version": 1,
    "metadata": {},
    "nodes": [],
    "edges": [],
    "variables": []
}
```

---

# Metadata

`metadata` содержит общие метаданные графа, не относящиеся непосредственно к исполнению отдельных узлов.

Например:

```json
{
    "metadata": {
        "name": "Регистрация",
        "description": "Первичная регистрация пользователя"
    }
}
```

Содержимое `metadata` должно оставаться минимальным.

Данные, являющиеся бизнес-логикой, не должны скрываться внутри произвольного metadata.

---

# Nodes

`nodes` содержит все узлы графа.

Каждый Node должен иметь уникальный идентификатор внутри конкретного Flow JSON.

Пример:

```json
{
    "nodes": [
        {
            "id": "welcome",
            "type": "message",
            "settings": {
                "text": "Здравствуйте!"
            }
        },
        {
            "id": "phone",
            "type": "input.contact",
            "settings": {}
        }
    ]
}
```

---

# Node.id

`Node.id` — стабильный идентификатор узла внутри графа.

Он используется:

- в `edges`;
- при сохранении состояния текущего Node;
- при диагностике;
- при выполнении Flow;
- при сравнении версий.

`Node.id` не должен зависеть от первичного ключа базы данных.

---

# Требования к Node.id

`Node.id` должен:

- быть уникальным внутри одного Flow JSON;
- оставаться стабильным после изменения положения Node в редакторе;
- не зависеть от порядка Node в массиве;
- не использовать ID базы данных.

При обычном перемещении Node его `id` не должен изменяться.

---

# Node.type

`Node.type` определяет тип Node.

Примеры:

```text
message
condition
input.text
input.contact
delay
flow.call
variable.set
http.request
```

`type` является публичным идентификатором и используется `NodeHandlerRegistry`.

Node JSON не должен содержать имя PHP-класса Handler.

---

# Node.settings

`settings` содержит параметры конкретного типа Node.

Например:

```json
{
    "id": "welcome",
    "type": "message",
    "settings": {
        "text": "Здравствуйте!"
    }
}
```

Для другого Node:

```json
{
    "id": "condition",
    "type": "condition",
    "settings": {
        "expression": "customer_age >= 18"
    }
}
```

Структура `settings` зависит от `type`.

---

# Общие требования к settings

`settings` должен содержать только параметры, необходимые конкретному Node.

Не рекомендуется помещать туда:

- состояние FlowSession;
- данные текущего пользователя;
- токены инфраструктуры;
- PostgreSQL ID;
- внутренние идентификаторы Laravel;
- служебное состояние Queue.

`settings` описывает конфигурацию Node, а не состояние его выполнения.

---

# Edges

`edges` описывает связи между Node.

Пример:

```json
{
    "edges": [
        {
            "id": "edge-1",
            "source": "welcome",
            "target": "phone"
        }
    ]
}
```

---

# Edge.id

Каждый Edge должен иметь стабильный идентификатор.

Он используется:

- редактором;
- диагностикой;
- сравнением версий;
- ссылками на переходы при необходимости.

---

# Edge.source

`source` содержит `id` исходного Node.

---

# Edge.target

`target` содержит `id` целевого Node.

---

# Дополнительные параметры Edge

Edge может содержать настройки перехода.

Например:

```json
{
    "id": "edge-1",
    "source": "condition",
    "target": "adult",
    "settings": {
        "condition": "age >= 18"
    }
}
```

Структура таких параметров определяется конкретной моделью перехода.

---

# Несколько исходящих Edge

Один Node может иметь несколько исходящих Edge.

Это используется для:

- условий;
- ветвлений;
- случайного выбора;
- распределения;
- переходов по значениям.

Например:

```text
Condition
   ├──> Adult
   └──> Minor
```

---

# Начальный Node

Начальный Node должен быть однозначно определён.

Рекомендуется хранить идентификатор стартового Node отдельно:

```json
{
    "start_node": "welcome"
}
```

Таким образом FlowEngine не должен угадывать стартовый Node по позиции элемента в массиве.

---

# End Node

Завершение Flow должно быть представлено явно.

Например:

```json
{
    "id": "finish",
    "type": "flow.end",
    "settings": {}
}
```

Использование отдельного конечного Node предпочтительно перед специальной логикой вида:

```text
отсутствует следующий Edge
```

Это делает граф более понятным для редактора и Compiler.

---

# FlowCall

Переход к другому Flow осуществляется через Node типа:

```text
flow.call
```

Например:

```json
{
    "id": "checkout",
    "type": "flow.call",
    "settings": {
        "flow": "checkout",
        "return": true
    }
}
```

В ссылках используется публичный `code` Flow.

Внутренний `flow_id` базы данных не используется.

---

# Ссылки на другие сущности

JSON-граф должен использовать публичные идентификаторы (`code`) для ссылок на другие бизнес-сущности.

Например:

```json
{
    "flow": "checkout"
}
```

или:

```json
{
    "variable": "customer_name"
}
```

или:

```json
{
    "media": "welcome-image"
}
```

Не следует использовать:

```json
{
    "flow_id": 42
}
```

если для сущности существует публичный `code`.

---

# Variables

`variables` может содержать описание переменных, которые используются конкретным Flow.

Например:

```json
{
    "variables": [
        {
            "code": "customer_name",
            "type": "string"
        },
        {
            "code": "age",
            "type": "number"
        }
    ]
}
```

Описание переменной не является её runtime-значением.

Значения выполнения находятся в `FlowSession`.

---

# Session State и JSON

Flow JSON никогда не должен содержать текущее состояние пользователя.

Запрещено хранить внутри Flow JSON:

```text
current_node
current_user
session_status
waiting_for
temporary_value
```

Эти данные относятся к `FlowSession`.

Таким образом:

```text
Flow JSON
    ↓
что выполняем

FlowSession
    ↓
как сейчас выполняем
```

---

# Editor Data

Некоторые данные необходимы визуальному редактору, но не влияют на выполнение сценария.

Например:

```json
{
    "position": {
        "x": 120,
        "y": 240
    }
}
```

или:

```json
{
    "width": 320,
    "height": 180
}
```

Такие данные могут храниться внутри Node или отдельной редакторской секции в зависимости от окончательной реализации редактора.

Они не должны влиять на бизнес-логику FlowEngine.

---

# Разделение Runtime и Editor данных

Вся информация Flow JSON должна принадлежать одной из двух категорий:

## Runtime Data

Используется FlowEngine.

Например:

```text
type
settings
edges
start_node
```

## Editor Data

Используется визуальным редактором.

Например:

```text
position
viewport
collapsed
display state
```

Редакторские данные не должны менять семантику выполнения Flow.

---

# Порядок элементов

Порядок элементов в:

```text
nodes
edges
variables
```

не должен влиять на выполнение Flow.

Смысл графа определяется:

```text
Node.id
Edge.source
Edge.target
```

а не позицией элемента в массиве.

Это позволяет безопасно сортировать JSON и выполнять детерминированные сравнения.

---

# Стабильность JSON

Редактор должен стремиться сохранять стабильную структуру JSON.

Не следует без необходимости:

- менять порядок Node;
- генерировать новые ID при каждом сохранении;
- менять формат пустых значений;
- преобразовывать эквивалентные структуры в разные представления.

Это уменьшает шум в Diff и облегчает:

- сравнение Draft;
- сравнение версий;
- аудит;
- экспорт;
- диагностику.

---

# Canonical JSON

Перед публикацией `FlowCompiler` может приводить JSON к каноническому представлению.

Например:

- стабильный порядок секций;
- стабильный порядок свойств;
- нормализация пустых значений;
- удаление редакторского мусора;
- проверка идентификаторов.

Это позволяет получать стабильный `checksum` для одинакового содержания Flow.

---

# Проверки Compiler

`FlowCompiler` должен проверять как минимум:

- существование `schema_version`;
- корректность структуры JSON;
- уникальность Node.id;
- уникальность Edge.id;
- существование `Edge.source`;
- существование `Edge.target`;
- существование `start_node`;
- существование целевых Flow для `flow.call`;
- корректность публичных `code`;
- наличие поддерживаемых Node.type;
- корректность обязательных settings;
- допустимость ссылок между Node;
- отсутствие структурных ошибок графа.

---

# Runtime Safety

Даже после успешной компиляции Runtime не должен предполагать, что данные физически невозможно повредить.

Поэтому:

- NodeHandler выполняет runtime-проверки;
- FlowEngine проверяет критические инварианты;
- повреждённая FlowVersion не должна приводить к неконтролируемому падению worker.

---

# Совместимость версий

Изменение формата Flow JSON сопровождается изменением:

```text
schema_version
```

Например:

```text
schema_version = 1
```

↓

```text
schema_version = 2
```

Старая версия формата не должна интерпретироваться как новая без явной миграции.

---

# Миграция формата

При изменении JSON-схемы могут использоваться миграции:

```text
schema v1

↓

Migration

↓

schema v2
```

Миграция может выполняться:

- при открытии Draft;
- при импорте;
- перед сохранением;
- отдельной служебной операцией.

Опубликованные `FlowVersion` не должны изменяться при миграции формата без создания новой версии.

---

# Импорт

При импорте Flow JSON система должна:

1. проверить `schema_version`;
2. проверить структуру;
3. проверить публичные ссылки;
4. проверить поддерживаемые Node;
5. разрешить конфликты `code`;
6. выполнить необходимые миграции;
7. создать Draft.

Импорт не должен автоматически публиковать сценарий.

---

# Экспорт

Экспорт должен содержать достаточно информации для восстановления сценария без зависимости от внутренних ID PostgreSQL.

Например:

```text
Flow code
Flow metadata
Flow JSON
Flow settings
Flow triggers
Required localization references
Required media references
```

Формат экспортного пакета будет определён отдельно.

---

# Безопасность

Flow JSON может содержать пользовательские тексты, URL и параметры внешних интеграций.

Поэтому:

- секреты не должны храниться непосредственно в JSON;
- токены API не должны попадать в Graph;
- пароли и ключи доступа должны храниться в защищённых настройках;
- пользовательские данные не должны записываться в опубликованный Flow JSON.

Например, вместо:

```json
{
    "api_key": "secret-value"
}
```

используется ссылка на безопасную конфигурацию:

```json
{
    "credential": "payment-api"
}
```

---

# Размер графа

Flow JSON должен оставаться достаточно компактным для:

- чтения из PostgreSQL;
- передачи через API;
- кэширования;
- загрузки редактором.

Большие бинарные данные не должны храниться внутри JSON.

Например:

```text
изображение
видео
документ
аудио
```

должны храниться в Media/Storage, а в графе использоваться через публичный `code`.

---

# Инварианты

Всегда должны соблюдаться следующие правила.

- Flow JSON имеет `schema_version`.
- Node.id уникален внутри графа.
- Edge.id уникален внутри графа.
- Все ссылки на Node используют Node.id.
- Ссылки на бизнес-сущности используют публичный `code`.
- Flow JSON не содержит runtime-состояние.
- Flow JSON не содержит секреты.
- Порядок элементов массивов не определяет семантику графа.
- Опубликованный Flow JSON неизменяем.
- Изменение схемы JSON приводит к изменению `schema_version`.
- Некорректный JSON не может попасть в опубликованную FlowVersion.

---

# Пример минимального Flow

```json
{
    "schema_version": 1,
    "metadata": {
        "name": "Приветствие"
    },
    "start_node": "welcome",
    "nodes": [
        {
            "id": "welcome",
            "type": "message",
            "settings": {
                "text": "Здравствуйте!"
            }
        },
        {
            "id": "finish",
            "type": "flow.end",
            "settings": {}
        }
    ],
    "edges": [
        {
            "id": "welcome-to-finish",
            "source": "welcome",
            "target": "finish"
        }
    ],
    "variables": []
}
```

---

# Пример FlowCall

```json
{
    "schema_version": 1,
    "start_node": "start",
    "nodes": [
        {
            "id": "start",
            "type": "flow.call",
            "settings": {
                "flow": "language-selection",
                "return": true
            }
        }
    ],
    "edges": [],
    "variables": []
}
```

# Будущие возможности

Формат допускает расширение:

```text
parallel branches
node groups
subgraphs
reusable modules
AI metadata
experiments
A/B configuration
feature flags
debug metadata
```

При изменении семантики должна использоваться новая `schema_version`.
