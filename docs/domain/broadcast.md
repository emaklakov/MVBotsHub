# Broadcast

**Документ:** `docs/domain/broadcast.md`

**Версия:** 1.0

**Статус:** Актуален

---

# Назначение

`Broadcast` представляет собой массовую рассылку сообщений участникам конкретного `Bot`.

Broadcast является агрегатом предметной области и отвечает за жизненный цикл одной рассылки: от подготовки и проверки аудитории до завершения или отмены.

Broadcast не отвечает за непосредственную отправку сообщений через Telegram.

---

# Ответственность

Broadcast отвечает за:

- определение Bot, от имени которого выполняется рассылка;
- определение аудитории;
- содержание рассылки;
- локализацию;
- планирование;
- управление жизненным циклом рассылки;
- фиксацию результата выполнения;
- возможность отмены рассылки до завершения.

Broadcast не отвечает за:

- непосредственный вызов Telegram API;
- управление Telegram rate limit;
- выполнение отдельных сетевых запросов;
- работу Redis;
- работу очередей;
- хранение полной истории сообщений Conversation.

---

# Принадлежность

Каждый Broadcast принадлежит одному Bot.

```text
Bot
 │
 └── Broadcast
```

Broadcast никогда не может использоваться одновременно несколькими Bot.

---

# Основные свойства

| Поле | Описание |
|------|----------|
| id | Внутренний идентификатор |
| bot_id | Bot-владелец |
| code | Уникальный публичный идентификатор |
| name | Название рассылки |
| status | Текущее состояние |
| content | Содержимое рассылки |
| audience | Определение аудитории |
| scheduled_at | Запланированное время запуска |
| started_at | Время фактического запуска |
| finished_at | Время завершения |
| created_by | User, создавший рассылку |
| created_at | Дата создания |
| updated_at | Дата изменения |
| deleted_at | Дата мягкого удаления |

---

# Публичный идентификатор

Каждый Broadcast может иметь уникальный `code` в пределах Bot.

Например:

```text
welcome-2026
black-friday
new-product
reengagement-july
```

`code` используется:

- при импорте и экспорте;
- в API;
- в логах;
- при интеграциях;
- для диагностики.

Внутренний `id` не используется как публичный идентификатор.

---

# Жизненный цикл

Broadcast проходит следующие состояния:

```text
Draft
  │
  ▼
Scheduled
  │
  ▼
Running
  │
  ▼
Completed
```

Дополнительные переходы:

```text
Draft ───────► Cancelled
Scheduled ───► Cancelled
Running ─────► Cancelled
Running ─────► Failed
```

---

# Draft

Broadcast находится в состоянии подготовки.

На этом этапе можно:

- изменить содержимое;
- изменить аудиторию;
- изменить локализацию;
- изменить настройки доставки;
- установить расписание;
- выполнить предварительную проверку.

Draft не отправляет сообщения.

---

# Scheduled

Рассылка подготовлена и ожидает запланированного времени запуска.

После перехода в `Scheduled` изменения, влияющие на уже рассчитанную аудиторию или содержимое, должны быть явно контролируемыми.

---

# Running

Рассылка находится в процессе выполнения.

На этом этапе система обрабатывает получателей и создаёт отдельные операции доставки.

---

# Completed

Все запланированные операции рассылки завершены.

Состояние является конечным.

---

# Cancelled

Рассылка была отменена до полного завершения.

Уже отправленные сообщения не отменяются.

Оставшиеся операции не должны запускаться.

---

# Failed

Рассылка не может быть завершена штатно из-за критической системной ошибки.

Причина должна быть зафиксирована.

Частично выполненная рассылка остаётся в истории.

---

# Аудитория

Broadcast работает с `BotMember`.

```text
Broadcast
   │
   ▼
BotMember
```

Аудитория может определяться:

- конкретным набором BotMember;
- фильтрами;
- сегментом;
- тегами;
- значениями переменных;
- статусом участника;
- языком;
- другими условиями.

Конкретный механизм построения аудитории описывается отдельным прикладным механизмом.

---

# Фиксация аудитории

После начала выполнения Broadcast аудитория не должна произвольно изменяться задним числом.

Система должна иметь возможность определить:

- кто должен был получить рассылку;
- кто получил сообщение;
- кто не получил;
- кто получил ошибку;
- кто был исключён.

Это необходимо для корректной статистики и повторной обработки.

---

# Исключения из аудитории

До начала отправки из аудитории могут быть исключены участники, которые:

- заблокировали бота;
- отписались от рассылок;
- недоступны по политике конкретного Broadcast;
- не соответствуют требованиям Bot;
- были удалены или архивированы в рамках допустимой политики.

Правила исключения определяются на уровне Application и Domain.

---

# Содержание рассылки

Broadcast содержит сообщение или набор локализованных сообщений, предназначенных для отправки участникам.

Содержимое может включать:

- текст;
- кнопки;
- изображения;
- документы;
- видео;
- другие поддерживаемые типы контента.

Формат конкретного сообщения должен быть независим от Telegram-specific API.

---

# Локализация

Broadcast может содержать несколько языковых вариантов.

Например:

```text
ru → "Здравствуйте!"
kk → "Сәлем!"
en → "Hello!"
```

При отправке конкретному BotMember выбирается эффективный язык этого участника.

При отсутствии перевода действует политика локализации Bot.

Например:

```text
BotMember language
        ↓
translation exists?
        │
   ┌────┴────┐
   │         │
  yes        no
   │         │
   ▼         ▼
translation  fallback
```

Конкретные правила локализации определяются модулем Localization.

---

# Планирование

Broadcast может запускаться:

- немедленно;
- в указанное время.

Для запланированной рассылки используется:

```text
scheduled_at
```

После перехода в `Running` изменение времени запуска не допускается.

---

# Массовая отправка

Broadcast не отправляет сообщения самостоятельно.

Он инициирует процесс, который выполняется через Application и Queue.

Общая схема:

```text
Broadcast
    │
    ▼
Application
    │
    ▼
Queue
    │
    ▼
Delivery Jobs
    │
    ▼
Telegram Gateway
```

---

# Telegram Rate Limit

Ограничения Telegram не являются бизнес-правилом самого Broadcast.

Broadcast только определяет:

> что необходимо отправить.

Infrastructure и Application отвечают за:

- ограничение скорости;
- повторные попытки;
- backoff;
- обработку временных ошибок Telegram;
- распределение нагрузки между очередями.

Таким образом Broadcast не зависит от конкретных ограничений транспорта.

---

# Результат рассылки

Для каждого получателя система должна иметь возможность определить результат операции:

```text
Pending
Sent
Failed
Skipped
Cancelled
```

Эти данные относятся к истории выполнения Broadcast, а не к самому агрегату Broadcast.

---

# Повторная попытка

Ошибка доставки одному получателю не должна приводить к остановке всей рассылки.

Допускается:

```text
Recipient A → Sent
Recipient B → Failed → Retry
Recipient C → Sent
```

Количество повторных попыток и стратегия backoff определяются Application/Infrastructure.

---

# Идемпотентность

Одно логическое сообщение Broadcast одному BotMember не должно быть отправлено повторно в результате повторной доставки Job или временного сбоя worker.

Система должна иметь уникальный идентификатор операции доставки.

Например:

```text
Broadcast
+
BotMember
+
Message
```

образует уникальный контекст операции.

---

# Отмена

Broadcast может быть отменён:

- до запуска;
- во время выполнения.

При отмене:

- новые операции доставки не создаются;
- уже завершённые операции сохраняются;
- выполняющиеся операции доводятся до контролируемого состояния.

Broadcast не может вернуться из `Completed` в активное состояние.

---

# Завершение

Broadcast считается завершённым, когда все запланированные операции находятся в конечных состояниях:

```text
Sent
Failed
Skipped
Cancelled
```

Состояние `Pending` не должно оставаться у завершённой рассылки.

---

# История

История выполнения Broadcast является неизменяемой.

После фиксации результата операции не должны произвольно переписываться.

Изменение результата доставки выполняется только через новое событие или новую операцию, если это требуется архитектурой.

---

# Удаление

Broadcast не удаляется физически.

Используется Soft Delete.

Удаление не должно приводить к потере:

- истории запуска;
- информации о получателях;
- статистики;
- результатов доставки.

---

# Инварианты

Всегда должны соблюдаться следующие правила.

- Broadcast принадлежит одному Bot.
- Broadcast не отправляет сообщения напрямую.
- Broadcast работает только с BotMember этого же Bot.
- После начала выполнения аудитория не должна незаметно изменяться.
- Завершённый Broadcast не возвращается в активное состояние.
- История операций доставки сохраняется.
- Физическое удаление Broadcast не выполняется.
- Повторная обработка одной Job не должна приводить к повторной отправке одного логического сообщения.
- Новые отправки выполняются через Application/Queue.
- Transport-specific логика не находится в Domain.

---

# Безопасность

Broadcast может содержать чувствительное содержимое и данные аудитории.

Поэтому:

- содержимое не должно попадать в обычные системные логи;
- персональные данные аудитории не должны логироваться без необходимости;
- секреты внешних интеграций не должны храниться в содержимом Broadcast;
- права User на конкретный Bot должны проверяться до создания и управления Broadcast.

---

# Масштабирование

Архитектура Broadcast должна позволять:

- обслуживать большие аудитории;
- параллельно обрабатывать несколько Broadcast;
- распределять доставку по очередям;
- повторять неуспешные операции;
- независимо масштабировать workers.

Broadcast не должен загружать всю аудиторию в память одного PHP-процесса.

---

# Будущие возможности

Архитектура допускает:

- сегментацию аудитории;
- A/B-рассылки;
- персонализацию;
- шаблоны;
- повторные рассылки;
- цепочки рассылок;
- расписания;
- ограничение частоты;
- контроль часовых поясов;
- аналитику конверсии;
- автоматические кампании.
