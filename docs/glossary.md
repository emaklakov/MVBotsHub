# Назначение

Настоящий документ определяет терминологию, используемую в проекте MVBotsHub.

Все документы проекта ДОЛЖНЫ использовать определения, приведённые в настоящем документе.

Использование одного термина в разных значениях НЕ ДОПУСКАЕТСЯ.

---

# Общие архитектурные термины

## Domain

Предметная область системы.

Domain описывает бизнес-модель платформы независимо от используемых технологий.

---

## Business Logic

Совокупность правил, ограничений и процессов предметной области.

Бизнес-логика определяет, **что** должно происходить в системе.

Бизнес-логика НЕ определяет, **как** это реализовано технически.

---

## Module

Логически независимая часть системы, отвечающая за конкретную область предметной области.

Примеры:

- Bot
- Person
- Flow
- Broadcast

---

## Aggregate

Главная сущность предметной области, обеспечивающая согласованность связанных данных.

Все изменения внутри агрегата происходят через Aggregate Root.

---

## Aggregate Root

Корневая сущность агрегата.

Только Aggregate Root может изменять внутреннее состояние агрегата.

---

## Entity

Объект предметной области, обладающий собственной идентичностью.

Две сущности считаются различными даже при совпадении всех остальных свойств.

---

## Value Object

Объект предметной области, не имеющий собственной идентичности.

Сравнение выполняется исключительно по значению.

Примеры:

- Phone
- LanguageCode
- Currency
- TimeRange

---

## Domain Service

Компонент Domain, содержащий бизнес-логику, которая не относится исключительно к одной сущности.

---

## Repository

Контракт доступа к агрегатам предметной области.

Domain определяет интерфейс репозитория.

Infrastructure предоставляет его реализацию.

---

## Domain Event

Событие, описывающее факт, уже произошедший внутри предметной области.

Например:

- BotCreated
- BroadcastStarted
- FlowFinished

---

## Use Case

Сценарий использования системы.

Use Case описывает последовательность действий для достижения конкретной цели пользователя.

Реализуется в слое Application.

---

## Application Service

Компонент слоя Application, координирующий выполнение одного или нескольких Use Case.

Application Service НЕ содержит бизнес-правил.

---

## Infrastructure

Слой, реализующий технические детали работы приложения.

Примеры:

- PostgreSQL
- Redis
- Telegraph
- файловая система

---

## Presentation

Слой взаимодействия с пользователями и внешними системами.

Примеры:

- MoonShine
- HTTP API
- Telegram Webhook
- Console Commands

---

# Термины предметной области

## User

Пользователь MVBotsHub.

Сотрудник, работающий с административной панелью.

User проходит авторизацию в системе.

User НЕ является пользователем Telegram-бота.

---

## Person

Реальный человек.

Person взаимодействует с одним или несколькими ботами.

Person существует независимо от конкретного Telegram-аккаунта.

Главным идентификатором Person является номер телефона.

---

## Bot

Логическая модель Telegram-бота внутри платформы.

Bot объединяет:

- участников;
- сценарии;
- настройки;
- локализацию;
- рассылки.

---

## BotAccess

Связь между User и Bot.

Определяет права конкретного пользователя системы на конкретного бота.

---

## BotMember

Участие Person в конкретном Bot.

BotMember хранит информацию, относящуюся исключительно к взаимодействию человека с данным ботом.

Например:

- telegram_id;
- chat_id;
- выбранный язык;
- текущую FlowSession.

---

## Conversation

Логический диалог между Bot и BotMember.

Conversation объединяет сообщения в единую историю общения.

---

## Message

Отдельное сообщение внутри Conversation.

Сообщение может быть входящим или исходящим.

---

## Flow

Описание сценария общения.

Flow определяет возможные переходы между шагами.

Flow НЕ хранит состояние выполнения.

---

## FlowSession

Экземпляр выполнения Flow.

FlowSession хранит текущее состояние прохождения сценария конкретным BotMember.

---

## Broadcast

Массовая отправка сообщений группе BotMember.

Broadcast выполняется с учётом ограничений Telegram.

---

## Localization

Совокупность переводов, используемых конкретным Bot.

---

## BotSettings

Настройки конкретного Bot.

Определяют поведение бота по умолчанию.

---

# Интеграции

## Telegram

Транспорт доставки сообщений.

Telegram НЕ является частью бизнес-модели.

---

## Telegraph

Библиотека интеграции Laravel с Telegram Bot API.

Telegraph относится к слою Infrastructure.

---

## MoonShine

Административный пользовательский интерфейс платформы.

MoonShine относится к слою Presentation.

---

# Технические термины

## DTO

Объект передачи данных между слоями приложения.

DTO НЕ содержит бизнес-логики.

---

## Queue

Механизм асинхронного выполнения задач.

---

## Job

Единица фоновой работы.

Job выполняется системой очередей.

---

## Event

Событие приложения.

Следует различать Domain Event и технические события Laravel.

---

## Listener

Обработчик события.

---

# Правила использования терминологии

Терминология проекта является частью архитектуры.

Все новые документы, комментарии к коду, имена классов, пространств имён и сущностей ДОЛЖНЫ использовать термины, определённые в настоящем документе.

Использование синонимов для одной и той же сущности НЕ ДОПУСКАЕТСЯ.

---

# Запрещённые термины

Во избежание неоднозначности в проекте запрещается использовать следующие термины.

| Не использовать | Использовать | Причина |
|-----------------|-------------|---------|
| Admin | User | Пользователь системы не обязательно является администратором. |
| Administrator | User | Роль определяется правами, а не названием сущности. |
| Client | Person | "Client" имеет множество значений (клиент компании, HTTP Client, API Client). |
| Customer | Person | Не каждый Person является клиентом компании. |
| Telegram User | Person или BotMember | Telegram — только транспорт. |
| Subscriber | BotMember | Человек взаимодействует с ботом, а не просто подписан на него. |
| Contact | Person | Contact — адресная книга, а не сущность предметной области. |
| Chat User | BotMember | Общение происходит в рамках конкретного бота. |
| Dialog | Conversation | Используется единый термин Conversation. |
| State | FlowSession | State слишком абстрактен. |
| Scenario State | FlowSession | Состояние принадлежит экземпляру выполнения сценария. |
| Service | Уточнить тип сервиса | Всегда использовать Domain Service, Application Service или Infrastructure Service. |
| Model | Уточнить понятие | Использовать Aggregate, Entity, Value Object или Eloquent Model в зависимости от контекста. |

# Правила именования

При проектировании новых модулей рекомендуется придерживаться следующих соглашений.

## Сущности

Используются существительные в единственном числе.

Примеры:

- Bot
- Person
- Conversation
- Message
- Broadcast

---

## Aggregate Root

Имя Aggregate Root совпадает с названием агрегата.

Например:

- Bot
- Conversation
- Broadcast

---

## Domain Events

Используется прошедшее время.

Примеры:

- BotCreated
- ConversationOpened
- BroadcastStarted
- MessageReceived

---

## Application Actions

Используется глагол, описывающий действие.

Примеры:

- CreateBot
- SendMessage
- StartBroadcast
- FinishFlow

---

## Jobs

Название ДОЛЖНО описывать выполняемое действие.

Примеры:

- SendTelegramMessageJob
- ProcessBroadcastJob
- UpdateWebhookJob

---

## Интерфейсы

Используются существительные.

Например:

- BotRepository
- ConversationRepository
- MessageGateway

Префикс `I` НЕ используется.

---

## Value Objects

Название отражает бизнес-смысл.

Примеры:

- Phone
- LanguageCode
- ChatIdentifier
- TelegramToken

---

## Enum

Название отражает предметную область.

Примеры:

- BotStatus
- BroadcastStatus
- ConversationStatus

Не рекомендуется использовать абстрактные названия вроде Status или Type.

---

# Изменение терминологии

Изменение существующей терминологии допускается только при выполнении следующих условий:

- принято архитектурное решение (ADR);
- обновлён настоящий документ;
- обновлена документация;
- терминология приведена к единому виду во всём проекте.

Использование двух различных терминов для обозначения одной сущности НЕ ДОПУСКАЕТСЯ.
