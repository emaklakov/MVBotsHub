# Назначение

Настоящий документ определяет архитектурные принципы проекта MVBotsHub.

Все архитектурные решения, принимаемые в ходе разработки, ДОЛЖНЫ соответствовать данным принципам.

Изменение принципов допускается только через принятие нового Architecture Decision Record (ADR).

---

# Цели архитектуры

Архитектура проекта ДОЛЖНА обеспечивать:

- простоту сопровождения;
- масштабируемость;
- расширяемость;
- тестируемость;
- независимость бизнес-логики;
- минимальную связанность компонентов;
- предсказуемость поведения системы.

---

# Основные принципы

## Модульный монолит

MVBotsHub представляет собой модульный монолит.

Приложение разворачивается как единый сервис, но состоит из независимых логических модулей.

Каждый модуль имеет собственную область ответственности.

---

## Domain First

Предметная область является основой всей системы.

Сначала проектируется бизнес-модель.

Затем проектируется архитектура.

Только после этого начинается реализация.

Бизнес-логика НЕ ДОЛЖНА определяться ограничениями фреймворка.

---

## Документация — источник истины

Документация является первичным источником информации о системе.

Последовательность разработки:

```text
Обсуждение

↓

Документация

↓

ADR (при необходимости)

↓

Проектирование

↓

Разработка

↓

Тестирование
```

Код ДОЛЖЕН соответствовать документации.

Не наоборот.

---

## Независимость Domain

Domain НЕ ДОЛЖЕН зависеть от:

- Laravel;
- Eloquent;
- MoonShine;
- Telegraph;
- Redis;
- PostgreSQL;
- Vue;
- HTTP;
- Telegram API.

Domain описывает исключительно бизнес-логику.

---

## Разделение ответственности

Каждый модуль ДОЛЖЕН иметь единственную область ответственности.

Если изменение требований приводит к изменению нескольких независимых частей системы, архитектура считается нарушенной.

---

## Dependency Inversion

Внешние компоненты зависят от Domain.

Domain НЕ зависит от внешних компонентов.

Все зависимости направлены внутрь системы.

---

## Минимальная связанность

Модули НЕ ДОЛЖНЫ знать внутреннее устройство друг друга.

Взаимодействие осуществляется только через публичные контракты.

---

## Высокая связность

Все элементы внутри одного модуля ДОЛЖНЫ решать одну общую задачу.

Не допускается объединение несвязанных обязанностей.

---

## Явные зависимости

Все зависимости ДОЛЖНЫ быть явными.

Скрытые зависимости, глобальные состояния и неявные связи НЕ РЕКОМЕНДУЮТСЯ.

---

# Архитектурные слои

Система разделяется на следующие логические слои.

```text
Presentation

↓

Application

↓

Domain

↑

Infrastructure
```

---

## Presentation

Отвечает за взаимодействие с внешним миром.

Примеры:

- MoonShine;
- HTTP API;
- Telegram Webhook;
- Console Commands.

Presentation НЕ содержит бизнес-логики.

---

## Application

Координирует выполнение сценариев использования.

Application:

- вызывает Domain;
- работает с репозиториями;
- запускает очереди;
- публикует события.

Application НЕ принимает бизнес-решений.

---

## Domain

Содержит предметную область.

Только здесь располагаются:

- агрегаты;
- сущности;
- value objects;
- доменные события;
- доменные сервисы;
- интерфейсы репозиториев.

---

## Infrastructure

Реализует технические детали.

Например:

- PostgreSQL;
- Redis;
- Telegraph;
- файловую систему;
- внешние API;
- очереди;
- кэш.

Infrastructure реализует интерфейсы Domain.

---

# Физическая структура проекта

Физическая структура каталогов МОЖЕТ отличаться от логической архитектуры.

Например:

```text
app/MoonShine
```

относится к слою Presentation, несмотря на физическое расположение в каталоге `app`.

Архитектурная роль определяется ответственностью, а не местом расположения файлов.

---

# Laravel

Laravel рассматривается как инфраструктурный фреймворк.

Архитектура проекта НЕ ДОЛЖНА строиться вокруг особенностей Laravel.

Использование возможностей Laravel допускается только в слоях Presentation, Application и Infrastructure.

---

# MoonShine

MoonShine является административным пользовательским интерфейсом.

MoonShine НЕ является частью Domain.

Замена MoonShine на другую административную панель НЕ ДОЛЖНА требовать изменения бизнес-логики.

---

# Telegram

Telegram рассматривается исключительно как транспорт доставки сообщений.

Бизнес-модель НЕ ДОЛЖНА зависеть от Telegram.

Поддержка других каналов связи (например, WhatsApp или Web Chat) ДОЛЖНА быть возможна без изменения Domain.

---

# Пользователи системы

Проект разделяет два типа пользователей.

## User

Сотрудник.

Работает в административной панели.

Использует систему управления.

---

## Person

Реальный человек.

Взаимодействует с ботами.

Person НЕ является пользователем административной панели.

---

# Управление доступом

Доступ сотрудников к ботам осуществляется через сущность BotAccess.

Bot НЕ хранит информацию о владельце.

Права определяются связью между User и Bot.

---

# Масштабирование

Архитектура ДОЛЖНА позволять:

- увеличение количества ботов;
- увеличение количества пользователей;
- увеличение количества сообщений;
- увеличение количества сценариев;
- горизонтальное масштабирование фоновых процессов.

Без изменения Domain.

---

# Архитектурные ограничения

В проекте запрещается:

- помещать бизнес-логику в контроллеры;
- помещать бизнес-логику в MoonShine Resources;
- помещать бизнес-логику в модели Eloquent;
- обращаться к Telegram API напрямую из Domain;
- обращаться к Redis напрямую из Domain;
- создавать новые каталоги верхнего уровня в `app/` без архитектурного обоснования и обновления документации.

---

Изменения документов со статусом Stable без соответствующего ADR НЕ ДОПУСКАЮТСЯ.
